# EdgeHunter — Decision Log

This file records *why* EdgeHunter is built the way it is. Entries are
append-only: existing entries are never edited or deleted, only superseded by
a new entry that references them. Decisions are referenced from `flow.md` and
`handoff.md` by their `D-NNN` number.

---

### D-001: Adopt a `src/` layout for the `edgehunter` package

- Date / phase / commit: 2026-10-08, Phase 0 (Repository Bootstrap and Engineering Foundation), ac9b228
- Context: The repository started empty. An installable package plus a console entry point are required, and later phases will add further subpackages (analysis, oracle, search, generators, execution, findings, ...). The physical layout had to be chosen before any code was written.
- Decision: Keep all importable code under `src/edgehunter/`; tests live in a separate top-level `tests/` directory.
- Why: The `src/` layout prevents accidental imports of working-copy modules (for example when running tools from the repository root) and forces contributors to validate the packaging configuration by installing the project. It is the layout the Python Packaging User Guide recommends for packages intended for distribution.
- Alternatives considered: Flat `edgehunter/` at repository root — works, but a stray `import edgehunter` can silently pick up the working tree instead of the installed package and hide packaging errors.
- Consequences: The CLI and tests require an editable install (`pip install -e ".[dev]"`) before `import edgehunter` works from an arbitrary directory. All future modules go under `src/edgehunter/<subpackage>/`.
- Files: pyproject.toml, src/edgehunter/, tests/

### D-002: Use setuptools with a dynamic version sourced from `edgehunter.__version__`

- Date / phase / commit: 2026-10-08, Phase 0 (Repository Bootstrap and Engineering Foundation), ac9b228
- Context: Packaging is defined in `pyproject.toml`. The version must be available both to the build backend and at runtime for `edgehunter --version`.
- Decision: Build backend `setuptools>=68` with `dynamic = ["version"]` and `[tool.setuptools.dynamic] version = { attr = "edgehunter.__version__" }`. `src/edgehunter/__init__.py` contains the literal `__version__ = "0.1.0"`.
- Why: setuptools is the most widely available backend and supports PEP 660 editable installs; reading the version via `attr` keeps a single source of truth. Because `__version__` is a simple literal, setuptools reads it without importing the package, so no runtime dependency is needed at build time.
- Alternatives considered: Static `version = "0.1.0"` in `pyproject.toml` — duplicates the version in two files that can drift; `hatchling` backend — modern and fast, but adds a less ubiquitous build requirement with no benefit at this stage; `flit` — infers metadata from docstrings, which conflicts with keeping `__init__.py` trivial.
- Consequences: Version bumps happen in exactly one place: `src/edgehunter/__init__.py`. `__init__.py` must not import runtime dependencies.
- Files: pyproject.toml, src/edgehunter/__init__.py

### D-003: Build the CLI with Typer

- Date / phase / commit: 2026-10-08, Phase 0 (Repository Bootstrap and Engineering Foundation), ac9b228
- Context: The CLI must expose `edgehunter --help`, `edgehunter --version`, and `edgehunter scan PATH` now, and is expected to grow nested commands later (`show`, `reproduce`, `report`, `export-test`). It also has to be testable in-process.
- Decision: Use Typer (`typer>=0.12`) as the CLI framework. Console entry point `edgehunter = "edgehunter.cli:main"`, where `main()` invokes the `typer.Typer` application. One root callback hosts the eager `--version` option; `scan` is a command under the same application.
- Why: Typer derives argument parsing from type hints, makes subcommand registration a decorator, and ships `typer.testing.CliRunner`, which invokes the application in-process and captures stdout and stderr separately. This keeps `src/edgehunter/cli.py` small and directly testable.
- Alternatives considered: `argparse` (standard library, zero dependencies) — nested subparsers, help formatting, and in-process exit handling all become manual code as commands accumulate; `click` directly — Typer is a thin layer over click, and using click directly adds boilerplate (explicit parameter declarations) with no capability we need beyond what Typer provides.
- Consequences: Runtime dependency on `typer` (and transitively `click`). CLI tests use `typer.testing.CliRunner`, not `click.testing.CliRunner`: the latter requires the underlying click command object and raises `AttributeError: 'Typer' object has no attribute 'name'` when handed a `typer.Typer` (verified with click 8.3.1 / typer 0.27.2). Shell-completion options are disabled (`add_completion=False`) to keep help output focused.
- Package: typer >=0.12 (verified working with typer 0.27.2 and click 8.3.1)
- Why this package: type-hint driven command definitions, subcommands, and an in-process test runner.
- Packages compared: argparse (standard library; more manual code for multi-command CLIs), click (more verbose API; Typer is built on it).
- Files: pyproject.toml, src/edgehunter/cli.py, tests/test_cli.py

### D-004: `scan` performs filesystem discovery only, with pruned non-source directories

- Date / phase / commit: 2026-10-08, Phase 0 (Repository Bootstrap and Engineering Foundation), ac9b228
- Context: The `scan` command must not pretend that analysis exists, but this phase also asks for the smallest genuinely useful behavior rather than a pure stub. Repository discovery (finding Python sources) is safe because it touches only the filesystem.
- Decision: `scan_repository()` walks a directory with `os.walk` (symlinks not followed), prunes directories named in `EXCLUDED_DIRECTORY_NAMES` and directories ending in `.egg-info`, collects `*.py` files in sorted order, and returns an immutable `ScanSummary`. A single `*.py` file is accepted as a target; any other regular file is rejected with `UnsupportedTargetError`. The CLI prints the summary and explicitly states that repository analysis is not implemented yet.
- Why: Real discovery is small, deterministic, and testable, and it establishes the `scanner` package that later phases build on. `os.walk` defaults to `followlinks=False`, which avoids symlink cycles and keeps the scan inside the requested tree. Exclusion by explicit name/suffix is conservative: unknown directories are always scanned.
- Alternatives considered: A pure placeholder that prints "not implemented" — no behavior to test, no extension point; AST parsing or module import — explicitly out of scope for this phase and unsafe (importing target code executes it); recursive `Path.rglob("*.py")` — cannot prune directory subtrees efficiently, while `os.walk` allows in-place pruning via the `dirnames` list.
- Consequences: The exclusion list is policy, not truth; repositories with unconventional vendor directories will include extra files. Discovery never imports or executes target code. Suffix matching is case-sensitive (a file named `X.PY` on Windows is not collected) — intentional, matches Python's module naming, revisit if it becomes an issue.
- Files: src/edgehunter/scanner/repository.py, src/edgehunter/scanner/__init__.py, src/edgehunter/cli.py, tests/test_repository_scanner.py, tests/test_cli.py

### D-005: Exit codes: 0 for success, 2 for invalid user input

- Date / phase / commit: 2026-10-08, Phase 0 (Repository Bootstrap and Engineering Foundation), ac9b228
- Context: Invalid input (missing path, non-Python file target) must fail with a non-zero status and without a traceback, while unexpected programming errors must stay visible.
- Decision: The `scan` command catches `ScanError` subclasses, prints `error: <message>` to stderr, and exits with code 2 (`EXIT_INVALID_INPUT` in `src/edgehunter/cli.py`). Unexpected exceptions are not caught: they surface as tracebacks with a non-zero exit.
- Why: Code 2 matches the convention used by argparse and click for usage errors, and keeps user errors distinguishable from internal bugs.
- Alternatives considered: Exit 1 for everything — loses the distinction between bad input and bugs; exit 0 with an error message — wrong, scripts could not detect failure.
- Consequences: Future commands should reuse code 2 for invalid input; new error families should subclass `ScanError` or a shared base when one exists.
- Files: src/edgehunter/cli.py, tests/test_cli.py

### D-006: Development tooling via the `dev` extra: pytest, ruff, mypy

- Date / phase / commit: 2026-10-08, Phase 0 (Repository Bootstrap and Engineering Foundation), ac9b228
- Context: This phase requires working test infrastructure, appropriate lint/format configuration, and typed code, without creating multiple competing dependency files.
- Decision: Declare development dependencies in `pyproject.toml` under `[project.optional-dependencies] dev` (`pytest>=8`, `ruff>=0.6`, `mypy>=1.10`), installed with `pip install -e ".[dev]"`. Configuration for pytest, ruff, and mypy lives in the same `pyproject.toml`.
- Why: A single authoritative dependency definition; extras are supported by every pip version, unlike PEP 735 dependency groups whose pip support is still recent. All three tools are actually executed in this session's verification and are enforced by the tests/lint/typecheck in `handoff.md`.
- Alternatives considered: `requirements-dev.txt` — second dependency source that can drift from `pyproject.toml`; PEP 735 `[dependency-groups]` — newer, unnecessary compatibility risk at this stage; skipping ruff/mypy — the phase asks for appropriate lint/format configuration and typed code.
- Consequences: Contributors must install the `dev` extra before running tests or checks. CI (future phase) should use the same command.
- Package: pytest >=8 — test runner.
- Package: ruff >=0.6 — linting and formatting.
- Package: mypy >=1.10 — static type checking.
- Why this package: pytest offers fixtures and parametrization with minimal boilerplate; ruff covers linting and formatting in one fast tool; mypy integrates directly with pyproject configuration and validates the type hints this project requires.
- Packages compared: unittest (stdlib; more boilerplate, weaker fixture model), nose (unmaintained); flake8 + black + isort (three tools and more configuration than ruff), pylint (slower, opinionated defaults); pyright (excellent but requires a Node toolchain), ty/pyre (less mature integration with pyproject).
- Files: pyproject.toml

### D-007: Verify the installed entry point with one subprocess test

- Date / phase / commit: 2026-10-08, Phase 0 (Repository Bootstrap and Engineering Foundation), ac9b228
- Context: In-process `CliRunner` tests bypass packaging: they call the Typer application directly and would pass even if `[project.scripts]` were wrong or `__main__.py` were broken.
- Decision: Keep the main CLI tests in-process (fast), and add a single end-to-end test (`test_python_dash_m_entry_point_reports_version` in `tests/test_cli.py`) that runs `python -m edgehunter --version` as a subprocess and checks its output and exit code.
- Why: Catches packaging and entry-point mistakes that in-process tests cannot see, at the cost of one subprocess per test run.
- Alternatives considered: Testing the installed `edgehunter` script name directly — depends on the virtual environment's `Scripts/` directory being on `PATH`, which is not guaranteed under pytest; no end-to-end test — leaves packaging untested.
- Consequences: This test requires the package to be installed (the editable install satisfies it); running pytest from a source checkout without installing makes this test fail while the in-process tests still pass.
- Files: tests/test_cli.py

### D-008: CLI code and tests import `typer.testing` only, never a standalone `click` package

- Date / phase / commit: 2026-10-08, Phase 0 (Repository Bootstrap and Engineering Foundation), ac9b228
- Context: While verifying the CLI, the Typer installed in the project virtual environment (typer 0.27.3) was found to vendor click internally (`typer._click`): `import click` raises `ModuleNotFoundError` in the venv, and the typer distribution declares no click requirement. Older Typer versions allowed by the `typer>=0.12` spec depend on a separate `click` package instead. Any CLI test must work under both layouts.
- Decision: Production and test code import only `typer` and `typer.testing` (`CliRunner`, `Result`); nothing imports `click` directly, and `click` is not declared in `pyproject.toml`.
- Why: `typer.testing.CliRunner` provides everything the tests need (in-process invocation, merged `output`, separate `stderr`) regardless of whether click is vendored or a separate distribution. A probe with typer 0.27.2 + click 8.3.1 (global environment) confirmed `click.testing.CliRunner` refuses a `typer.Typer` object with `AttributeError: 'Typer' object has no attribute 'name'`, so importing click offered no benefit.
- Alternatives considered: Declaring `click` as a direct test dependency and using `click.testing.CliRunner` — imports an object Typer does not promise to expose and would diverge across Typer versions.
- Consequences: Future CLI code and tests must not `import click`; use `typer.testing` and Typer's own helpers. The `typer>=0.12` floor admits versions both with and without vendored click; this decision keeps the project compatible with both.
- Files: tests/test_cli.py, decisions.md

### D-009: Split scanner analysis into models.py, targets.py, and ast_parser.py; add `analyze_repository()`

- Date / phase / commit: 2026-10-08, Phase 1 (Repository Scanner + Safe AST Extraction), 82d42f3
- Context: Phase 1 requires structural facts (functions, classes, methods, parameters, annotations, decorators, line spans) from every discovered Python file without executing it. Phase 0 had a single `repository.py` whose only responsibility was filesystem discovery.
- Decision: Add three modules under `src/edgehunter/scanner/`: `models.py` (frozen dataclasses and enums), `targets.py` (AST to classes/callables), `ast_parser.py` (safe source read + `ast.parse` + issue capture). Add `RepositoryAnalysis` and `analyze_repository()` to `repository.py`. `ScanSummary` and `scan_repository()` keep their Phase 0 signatures and behavior unchanged; `RepositoryAnalysis` composes a `ScanSummary` (`discovery`) with a tuple of `ModuleAnalysis` and adds derived counters.
- Why: The responsibilities differ (data structures, AST traversal, file-level analysis, repository orchestration), and the phase's recommended structure matches this split. Keeping `scan_repository()` untouched preserves every Phase 0 test and any external caller; new capability is purely additive.
- Alternatives considered: Putting everything in `repository.py` (one growing module with three responsibilities, harder to test in isolation); extending `ScanSummary` directly with modules/stats (makes "discovery-only" results ambiguous with "no modules found", and mutates a Phase 0 contract); placing `RepositoryAnalysis` in `models.py` (would require moving `ScanSummary` there to avoid a circular import between `models` and `repository`, a larger refactor than the phase needs).
- Consequences: Future analysis stages should add their own modules rather than growing `repository.py`; `RepositoryAnalysis` is the stable aggregate the CLI and later phases consume. `models.py` must stay free of runtime behaviour (no evaluation of annotations or defaults).
- Files: src/edgehunter/scanner/models.py, src/edgehunter/scanner/targets.py, src/edgehunter/scanner/ast_parser.py, src/edgehunter/scanner/repository.py, src/edgehunter/scanner/__init__.py, tests/test_ast_parser.py, tests/test_repository_analysis.py

### D-010: Target model and scope-aware classification rules

- Date / phase / commit: 2026-10-08, Phase 1 (Repository Scanner + Safe AST Extraction), 82d42f3
- Context: Later phases need to distinguish functions, async functions, methods, async methods, and nested definitions, with deterministic source-local names and reproducible ordering.
- Decision: `FunctionInfo` records `name`, `qualified_name`, `TargetKind` (six values), `lineno`/`end_lineno`, `is_async`, `owner`, `parameters`, `return_annotation`, and `decorators`. Classification uses the *immediate lexical scope*: directly inside a class body it is a method; directly inside a function body it is a nested function; at module scope it is a function; async variants are selected when the definition is `async def`. "Directly" ignores compound statements (`if`/`try`/loops/`with`/`match`), which do not change scope. `qualified_name` joins lexical names with dots (`Outer.Inner.run`, `outer.inner`). `owner` is set only for direct methods (the dotted class path); nested functions have no owner. Functions inside one module are flattened into a single tuple sorted by `(lineno, qualified_name)`; classes are sorted the same way. `ModuleAnalysis.functions` contains all callables (including methods and nested functions); `ClassInfo` does not duplicate them.
- Why: The classification rule is deterministic, easy to explain, and matches how Python name binding works lexically. `(lineno, qualified_name)` sorting makes output stable even if the AST traversal order ever changes. Flattening avoids duplicating method objects inside `ClassInfo` while `owner` keeps the class link.
- Alternatives considered: Full import-system qualified names (requires module path resolution, explicitly out of scope); classifying nested definitions by their own `def`/`async def` only (loses the method/nested distinction the phase requires); sorting by qualified name only (loses source locality, which later reporting depends on).
- Consequences: "Functions" statistics include nested functions but not methods; methods are counted separately. A later phase that needs true package-qualified names must build them on top of `qualified_name`, not replace it. Classes defined inside functions keep function names in their qualified path (`outer.Helper`), which is intentional.
- Files: src/edgehunter/scanner/models.py, src/edgehunter/scanner/targets.py, tests/test_ast_parser.py, tests/test_repository_analysis.py

### D-011: Read Python source with `tokenize.open` (PEP 263 encoding detection)

- Date / phase / commit: 2026-10-08, Phase 1 (Repository Scanner + Safe AST Extraction), 82d42f3
- Context: Python source files are not guaranteed to be UTF-8; they may declare an encoding with a coding cookie or a BOM. Reading with a hard-coded encoding would mislabel valid files as broken.
- Decision: `_read_source()` in `ast_parser.py` uses `tokenize.open(path)`, which implements Python's own source encoding rules (BOM and PEP 263 coding cookies), then returns the decoded text. Decoding failures (`UnicodeDecodeError`), unreadable files (`OSError`), and unknown/invalid declared encodings (`SyntaxError` from `tokenize`) become a structured `ReadIssue`; they are never mislabeled as syntax errors.
- Why: `tokenize.open` applies exactly the rules the Python interpreter uses to read source, without executing anything, and closing is handled by the context manager. It requires only the standard library.
- Alternatives considered: `Path.read_text(encoding="utf-8")` (fails on legacy encodings that Python itself accepts); manual BOM/cookie detection (reimplements CPython behaviour with no benefit); `ast.parse` of raw bytes (would silently pick an encoding we cannot report on and gives no distinct read/parse error stage).
- Consequences: Read failures carry the original exception message (for example `'ascii' codec can't decode ...`), which the CLI prints verbatim. Future phases that open source files should reuse the same mechanism.
- Files: src/edgehunter/scanner/ast_parser.py, tests/test_ast_parser.py, tests/test_repository_analysis.py

### D-012: Separate `SyntaxIssue` and `ReadIssue`; one bad file never aborts the scan

- Date / phase / commit: 2026-10-08, Phase 1 (Repository Scanner + Safe AST Extraction), 82d42f3
- Context: A repository may contain unparseable or unreadable files. The phase requires these to be visible, structured, and unable to crash the whole scan, and encoding/read failures must not be reported as syntax errors.
- Decision: `ModuleAnalysis` carries at most one of `syntax_issue: SyntaxIssue | None` (line, column, message taken from `ast.parse`'s `SyntaxError`: `lineno`, `offset`, `msg`) and `read_issue: ReadIssue | None` (message from the read/decode exception). Both yield a normal `ModuleAnalysis` with empty targets; analysis continues with the remaining files. `is_parsed` is true only when both are `None`.
- Why: Distinguishing the two failure modes lets the CLI report them honestly in separate sections, and per-file result objects keep the repository loop free of exception control flow. `ast.parse`'s `msg` is used instead of `str(exc)` because the latter embeds filename/line text.
- Alternatives considered: Raising on first failure (loses all later results, contradicts the requirement); a single generic issue type with a kind field (viable, but two frozen types make the line/column availability explicit and type-checkable); normalizing or rewriting Python's messages (the phase forbids inventing messages).
- Consequences: The CLI exit code is 1 when `issue_count > 0` (see D-013). `SyntaxIssue.line`/`column` stay `int | None` because Python does not guarantee them. Read issues deliberately carry no line number.
- Files: src/edgehunter/scanner/models.py, src/edgehunter/scanner/ast_parser.py, src/edgehunter/cli.py, tests/test_ast_parser.py, tests/test_cli.py

### D-013: CLI `scan` reports AST statistics, supports `--targets`, and adds exit code 1

- Date / phase / commit: 2026-10-08, Phase 1 (Repository Scanner + Safe AST Extraction), 82d42f3
- Context: `edgehunter scan` previously printed discovery counts plus a notice that analysis was not implemented. Phase 1 makes analysis real, so the output and exit-code contract must reflect it. D-005 established 0 = success and 2 = invalid input but said nothing about completed scans with unparseable files.
- Decision: `scan` now calls `analyze_repository()` and prints discovered/parsed/syntax-issue/read-issue counts, class/function/method/async/callable-target counts, and (for directories) excluded-directory count. It prints `Syntax issues` and `Read issues` sections when present. A new `--targets` option lists every callable target as `relative/path.py:line` plus its static signature (`signature` property on `FunctionInfo`, defaults rendered as `...`). Exit codes: 0 = all discovered files parsed, 1 = scan completed with at least one syntax or read issue (`EXIT_SCAN_ISSUES`), 2 = invalid input (`EXIT_INVALID_INPUT`, unchanged). Invalid paths/unsupported targets still print `error: ...` to stderr with no traceback.
- Why: The phase requires visible syntax failures, deliberate exit codes, and a target listing. Exit 1 gives scripts a way to detect incomplete analysis without conflating it with bad user input (2) or success (0), extending D-005 rather than reversing it.
- Alternatives considered: Keep exit 0 for scans with issues (hides failures from CI); exit 2 for parse failures (would make a completed scan indistinguishable from a bad path); always listing targets without a flag (noisy for large repositories), separate `list` command (premature; the phase asks for an option).
- Consequences: Two Phase 0 CLI tests were updated for the new output (`test_scan_directory_succeeds_and_reports_counts`, `test_scan_single_python_file_succeeds`); the removed "not implemented" notice is asserted absent. New tests cover stats, `--targets`, and exit code 1 for both issue kinds. Later commands should follow the same 0/1/2 convention.
- Files: src/edgehunter/cli.py, tests/test_cli.py

### D-014: AST analysis uses only the standard library; no third-party parser dependency

- Date / phase / commit: 2026-10-08, Phase 1 (Repository Scanner + Safe AST Extraction), 82d42f3
- Context: Phase 1 needs to parse arbitrary Python 3 source and extract syntax facts. The phase allows a third-party AST dependency only with a demonstrated need the standard library cannot satisfy.
- Decision: Use the standard library only: `ast` for parsing and `ast.unparse` for rendering annotations/decorators/bases, `tokenize` for encoding detection. No new runtime dependencies were added.
- Why: `ast.parse` accepts every syntax the running interpreter accepts and never imports analyzed modules. `ast.unparse` round-trips the expressions needed here. Both are guaranteed present, fast enough, and keep the dependency surface at `typer` only (Phase 0).
- Alternatives considered: `astroid` (adds inference and dependencies, unnecessary at this stage); `LibCST` (lossless CST, heavier, aimed at rewriting); `parso` (multiple-version grammar support not needed); `tree-sitter` (native dependency, non-Python grammar versions, overkill). All were rejected because nothing in this phase needs error-recovering parsing or round-trip rewriting.
- Consequences: Analysis is tied to the running interpreter's grammar (a file using a newer syntax than the running Python reports a syntax issue; documented as a known limit). If a later phase needs to parse across Python versions or preserve formatting, that requires a new decision.
- Files: pyproject.toml (unchanged; recorded for the record), src/edgehunter/scanner/ast_parser.py, src/edgehunter/scanner/targets.py

### D-015: Add an `analysis` layer and split the scanner pipeline so each file is read and parsed once

- Date / phase / commit: 2026-10-08, Phase 2 (Static Semantic Analysis + Boundary Mining), b538557
- Context: Phase 1 already reads a file with `tokenize.open` and parses it with `ast.parse`, then discards the AST. Phase 2 needs that same AST to extract semantic facts. Re-parsing every file would duplicate all I/O and parsing work, and a second, independent safe-parsing implementation was explicitly ruled out.
- Decision: (1) Add a sibling package `src/edgehunter/analysis/` with `models.py`, `semantics.py`, `boundaries.py`, and `repository.py`; `scanner` keeps answering "what exists", `analysis` answers "which semantic facts exist". (2) Split the scanner pipeline: `parse_source_file()` returns a `SourceFile` carrying the parsed `ast.Module` (or a structured issue); `build_module_analysis()` derives structural facts from it; `collect_callable_nodes()` returns `CallableNode` pairs so semantic facts are attributed to exactly the targets the structural scanner discovered; `analyze_python_file()` remains as the Phase 1 convenience wrapper. (3) Move the shared `ast.unparse` rendering with its fallback into `scanner/rendering.py`. (4) `analysis/repository.py::analyze_repository_semantics()` reads and parses each discovered file once, then derives both structure and semantics, and returns `RepositorySemantics` with the scanner's `RepositoryAnalysis` embedded as `.structure`. No new runtime dependency (standard library only, consistent with D-014).
- Why: One read/parse per file keeps the scan cost linear and guarantees the structural and semantic views of a file can never disagree. Reusing `collect_callable_nodes()` removes any possibility of a second, divergent implementation of the qualified-name and scope rules from D-010 — a real divergence risk, since boundary mining must know a target's parameters. `SourceFile.tree` is internal pipeline state and is never part of the public scanner models or CLI output. A test (`test_each_source_file_is_read_once`) locks the single-read property in place.
- Alternatives considered: Keeping the AST inside `ModuleAnalysis` (leaks a raw AST into a Phase 1 public model and its equality/repr); re-parsing in the analysis layer (duplicates the safe-read/parse logic and doubles I/O); having `analysis` re-derive qualified names itself (second implementation of D-010's scope rules, guaranteed to drift); putting semantic extraction in `scanner/targets.py` (would make `scanner` depend on semantic concepts and blur the "what exists" boundary).
- Consequences: `scanner/ast_parser.py` gained `SourceFile`/`parse_source_file`/`build_module_analysis` and `scanner/targets.py` gained `CallableNode`/`collect_callable_nodes`; Phase 1 public behavior and all 52 Phase 1 tests are unchanged (verified immediately after the refactor). `analysis` depends on `scanner`, never the reverse. The CLI now calls `analyze_repository_semantics()` and reads structural counts from `.structure`.
- Files: src/edgehunter/analysis/__init__.py, src/edgehunter/analysis/models.py, src/edgehunter/analysis/semantics.py, src/edgehunter/analysis/boundaries.py, src/edgehunter/analysis/repository.py, src/edgehunter/scanner/rendering.py, src/edgehunter/scanner/ast_parser.py, src/edgehunter/scanner/targets.py, src/edgehunter/scanner/__init__.py

### D-016: Semantic extraction rules (predicates, comparisons, constants, arithmetic)

- Date / phase / commit: 2026-10-08, Phase 2 (Static Semantic Analysis + Boundary Mining), b538557
- Context: Phase 2 must turn syntax into deterministic, test-relevant facts, with classification rules precise enough to implement identically twice.
- Decision: Facts are collected per callable target. Predicates come from `if`, `while`, and `assert` only (`PredicateKind`); `elif` yields its own predicate through nested `ast.If`. Each predicate keeps its containing expression *and* every comparison inside it, including inside `and`/`or` operands. A chained comparison is decomposed into adjacent pairs (`0 < x <= 10` yields `0 < x` and `x <= 10`), never into `0 < 10`. Operators are mapped to a stable `ComparisonOperator` enum (`<`, `<=`, `>`, `>=`, `==`, `!=`, `is`, `is not`, `in`, `not in`). Constants are recorded per literal occurrence with a `ConstantKind` vocabulary of integer, float, complex, string, bytes, bool, none; `bool` is tested before `int` so `True` is never numeric, and `...` (Ellipsis) is deliberately not recorded because it is a stub placeholder rather than a value literal. Signed numeric literals (`-1`, `+0.5`) are recognized through an explicit `UnaryOp`-over-`Constant` helper; no `eval`/`literal_eval` is used anywhere. Arithmetic is recorded as *maximal* subexpressions: a `BinOp` whose ancestor is also an arithmetic `BinOp` is not recorded separately, so `(x + y) * 2` is one `ArithmeticInfo` carrying both operators, avoiding double counting. Contexts are return, assignment, annotated assignment, augmented assignment, or plain expression. No simplification, folding, or algebra is performed. Traversal stops at nested `FunctionDef`/`AsyncFunctionDef`/`ClassDef`/`Lambda`, so an inner callable's facts are never attributed to its parent, and module- or class-level conditions belong to no target.
- Why: Recording the containing predicate alongside its comparisons preserves boolean structure without attempting satisfiability solving. Recording maximal arithmetic keeps counts meaningful (one expression, one record) while still exposing every operator involved. `bool`-before-`int` is required because `bool` subclasses `int` at runtime; the test `test_bool_literal_is_not_numeric` pins it.
- Alternatives considered: Recording nested arithmetic separately (double counts `(x + y) * 2` as two expressions); omitting comparisons from boolean operands (loses real constraints); recording `...` as a constant (pollutes every stub body with a meaningless fact); classifying constants by `type(value)` only (misclassifies `bool` as `integer`).
- Consequences: Comparison facts only originate inside predicates, so a comparison outside `if`/`while`/`assert` (for example `y = x > 3`) is not recorded as a comparison; it is still visible as part of an `ArithmeticInfo`/expression text if it appears there. `assert` predicates are recorded as syntax only: no property or invariant claim is made anywhere (that is a later phase).
- Files: src/edgehunter/analysis/models.py, src/edgehunter/analysis/semantics.py, tests/test_semantics.py

### D-017: Boundary candidate vocabulary and derivation rules

- Date / phase / commit: 2026-10-08, Phase 2 (Static Semantic Analysis + Boundary Mining), b538557
- Context: Boundary mining must propose regions worth testing without claiming a defect, without evaluating anything, and without inventing numbers that are only meaningful for one numeric type.
- Decision: A finite `BoundaryKind` vocabulary: comparison-derived `JUST_BELOW`, `AT_BOUNDARY`, `JUST_ABOVE`; generic numeric `ZERO`, `ONE`, `NEGATIVE_ONE`, `NEGATIVE_ZERO`, `NAN`, `POSITIVE_INFINITY`, `NEGATIVE_INFINITY`. Derivation rules: inequalities (`<`, `<=`, `>`, `>=`) with an ordered reference yield below/at/above; equality and inequality-difference (`==`, `!=`) yield `AT_BOUNDARY` only; `is`, `is not`, `in`, `not in` yield nothing. Generic numeric candidates are derived only when a parameter's annotation text is exactly `int` or `float`, and only for positional-only, positional-or-keyword, and keyword-only parameters. References stay symbolic: for `amount <= balance` the candidate is "amount at balance", never `balance - 1`, because the correct step depends on a type this phase does not resolve. Every candidate records `origin` (`COMPARISON`/`NUMERIC`), the rendering `reason` (static evidence, never a bug claim), and every source line that suggested it.
- Why: `int` yields zero/one/negative-one; `float` additionally yields negative zero, NaN, and both infinities, which is exactly the edge region a float parameter can be mishandled at. Keeping references symbolic is what lets one boundary description serve floats, `Decimal`, dates, and custom numerics in a later phase. `==`/`!=` deliberately do not synthesize numeric neighbors, so `status_code == 200` does not invent `199`/`201`.
- Alternatives considered: Materializing concrete values such as `17/18/19` for `age >= 18` (premature: needs type resolution and would bake in an integer step); deriving numeric neighbors for equality (unsound for any non-numeric or mixed type); omitting generic NaN/infinity candidates (they are a primary float boundary region); applying generic candidates to `*args`/`**kwargs` (a variadic parameter is a sequence, not one value).
- Consequences: Scanning EdgeHunter's own source yields very few candidates because almost nothing is annotated exactly `int`/`float`; that is the conservative rule working as designed, not a defect. Annotation matching is textual, so `Optional[int]`, `int | None`, `Annotated[int, ...]`, `Decimal`, and `numpy.int64` receive no generic candidates while still getting comparison-derived ones.
- Files: src/edgehunter/analysis/models.py, src/edgehunter/analysis/boundaries.py, tests/test_boundaries.py

### D-018: Parameter normalization, safe-reference rule, deduplication, and ordering

- Date / phase / commit: 2026-10-08, Phase 2 (Static Semantic Analysis + Boundary Mining), b538557
- Context: Boundary candidates are only useful when the interesting parameter is the subject of the boundary, and they must be conservative about references whose value cannot be known statically.
- Decision: For each comparison, a candidate is mined only when one side is a plain name that is a declared parameter. That side becomes the subject; if it was the right side, the operator is inverted using the exact table `< -> >`, `<= -> >=`, `> -> <`, `>= -> <=`, `== -> ==`, `!= -> !=`; `is`, `is not`, `in`, and `not in` are never inverted (they return no candidate). When both sides are parameters the syntactic left side wins, so no inverse relational candidate is generated. The opposite side must be a stable reference — a literal, a bare name, or a plain dotted name chain (determined from the AST, not from the rendered text, so `self.limit` is allowed but `f().x` and `items[i]` are not). A non-numeric literal reference (for example `'admin'`) yields candidates only for `==`/`!=`. Candidates are deduplicated by `(parameter, kind, reference)` within a target, with every evidence line preserved and sorted. Final ordering is `(parameter, boundary-kind rank, reference)` where the rank table puts comparison-derived kinds before generic numeric kinds.
- Why: Normalizing `0 <= amount` to "amount at 0" is what makes boundary mining useful regardless of how the source happens to be written. Restricting inversion to operators where the reversal is provably equivalent avoids unsound rewrites of identity and membership. Rejecting call/subscript/complex references keeps every reference materializable later without execution, while still recording the comparison itself as a fact. Preferring the left side avoids emitting both `amount` relative to `balance` and the redundant inverse.
- Alternatives considered: Emitting the inverse relational candidate as well (duplicate noise); inverting `is`/`in` (unsound or meaningless); accepting any expression as a reference (a future generator could not materialize it safely); deduplicating by rendered description text (kind and reference belong in the key); sorting alphabetically by kind (would print `NaN` before `just below`, which reads badly and hides the comparison evidence).
- Consequences: `test_call_reference_is_never_invoked_and_produces_no_candidate` and `test_complex_reference_produces_no_candidate` pin the conservative behavior. Comparisons with neither side a parameter (for example `config.limit < 10`) produce no candidate but remain visible as semantic facts.
- Files: src/edgehunter/analysis/boundaries.py, tests/test_boundaries.py

### D-020: Deliberately unsupported semantics are recorded as limitations, not approximated

### D-022: Structural risk formula, caps, and ranking

- Date / phase / commit: 2026-10-08, Phase 3 (Structural Risk Scoring + Oracle / Property Mining), 12d82df
- Context: EdgeHunter needs a deterministic way to order targets for testing attention. The score must be explainable, must not pretend to be a probability, and must not be swamped by one noisy feature.
- Decision: `analysis/risk.py` computes `TargetRiskProfile` from five named contributions, each capped: predicates +6 each (cap 30), arithmetic expressions +4 each (cap 20), boundary groups +4 each (cap 20), input parameters +3 each (cap 15), source span +3 per started block of 20 lines (cap 15); total capped at 100. A boundary *group* is a unique `(parameter, reference)` pair, so the three below/at/above kinds for one reference are one group and a float parameter's seven generic numeric values are one group. Source span comes from the scanner's `lineno`/`end_lineno` (`end_lineno - lineno + 1`, falling back to a single line when unavailable) so no source is re-read. For methods, a first parameter named `self`/`cls` is excluded from the input-parameter feature. Ranking is `score` descending, then relative POSIX path, then line, then qualified name.
- Why: The weights are the phase's proposed baseline, adopted unchanged after inspecting the models; capping each feature stops a float parameter's seven generic candidates from dominating. Grouping by `(parameter, reference)` captures distinct constraints instead of counting kinds. Excluding the receiver follows the phase rule and matches how input-parameter count is meant to read. Ordering is total and deterministic, so equal scores never depend on traversal order.
- Alternatives considered: counting every boundary candidate instead of groups (float annotations alone would swamp the score); using cyclomatic complexity or a complexity library (out of scope, adds a dependency for a transparent heuristic); learned or probabilistic weights (no calibration data exists, and it would contaminate the deterministic baseline); a normalized 0-1 score (would imply calibration that does not exist).
- Consequences: The score is explicitly a search-priority heuristic; the CLI prints "Search-priority heuristic, not a probability of a bug." Scores are comparable within one EdgeHunter version and are not expected to be stable across scoring changes, so benchmark artifacts must record the version and formula. Test functions are scored too, because risk is structural and phase 3 deliberately does not infer that tests matter more.
- Files: src/edgehunter/analysis/risk.py, src/edgehunter/analysis/models.py, src/edgehunter/analysis/__init__.py, tests/test_risk.py

### D-023: Oracle models split by evidence source, with categorical strength

- Date / phase / commit: 2026-10-08, Phase 3 (Structural Risk Scoring + Oracle / Property Mining), 12d82df
- Context: Oracle evidence comes from two structurally different places: statements inside production callables, and expectations inside test files. One wide "property" record with many optional fields would blur what each kind of evidence actually is.
- Decision: `oracle/models.py` defines `PropertyKind` (`asserted_condition`, `rejection_rule`, `example_expectation`, `example_raises`), `ExpectedOutcome`, `OracleStrength`, `OracleEvidenceKind`, `TargetResolution`, `OracleSupport`, and two narrow records: `ProductionPropertyCandidate` (always has a resolved `target`, plus `condition`, `message`, `expected_outcome`, `exception`) and `TestExpectationCandidate` (has `callee`, `call_expression`, optional operator/expected/exception, `resolution`, `resolution_reason`, optional `target`). Only `STRONG` strength exists, because every implemented source is explicit evidence.

### D-024: Production oracle rules — assertions and conservative validation guards

- Date / phase / commit: 2026-10-08, Phase 3 (Structural Risk Scoring + Oracle / Property Mining), 12d82df
- Context: Phase 2 already extracts `assert` predicates, so assertion evidence should reuse that work. Validation guards must be recognized conservatively: a false rejection rule is a false oracle.
- Decision: `extract_production_properties()` mines, per callable target: (a) an `ASSERTED_CONDITION` for every Phase 2 `assert` predicate, reusing its rendered condition and line, plus the assertion message when it is a literal string or otherwise stored as its rendered syntax (never evaluated; omitted when the line holds more than one `assert`); (b) a `REJECTION_RULE` for every `if` whose body is exactly one `raise` statement, recording the trigger syntax, the expected outcome `raises`, and the exception syntax. Exception extraction: a bare `raise Name` records `Name`; `raise Name(...)` records `Name` only when it ends in `Error`/`Exception`/`Warning` (otherwise the exception is left `None` and the rendered call is kept as evidence detail, so `raise make_exception()` claims no type); `raise a.b.X(...)` records the dotted text; a bare `raise` records no exception and the detail "re-raises"; anything more complex records no exception. Assertions are recorded as "the code expects this when execution reaches it" and are never restated as a universal input contract. Modules whose filename matches the test-file rule are skipped here, because an `assert` inside a test function is evidence about the tested callable and is mined as a test expectation instead.
- Why: Reusing Phase 2 predicates means assertion conditions, lines, and ownership cannot drift from the semantic layer. Requiring a single-statement `raise` body deliberately rejects `if cond: log(); raise` and `if cond: return None`, so only unambiguous rejection paths become rules. Not inverting a rule into "the opposite condition is valid" preserves the difference between "this path raises" and "everything else works".
- Alternatives considered: mining guards whose body is a block ending in `raise` (looks natural but admits logging/cleanup paths); treating `except` re-raise as validation (it is exception flow, out of scope); extracting exception classes by importing them (unsafe and unnecessary); keeping production mining in test files (double-counts one statement as two different oracles).
- Consequences: Repositories using multi-statement validation guards yield fewer rules than a human would consider obvious; that under-reporting is intentional and documented. Exception classes are never imported or instantiated.
- Files: src/edgehunter/oracle/production.py, tests/test_oracle_production.py

### D-025: Test-file recognition and the mined expectation subset

- Date / phase / commit: 2026-10-08, Phase 3 (Structural Risk Scoring + Oracle / Property Mining), 12d82df
- Context: Existing tests carry real oracle evidence, but interpreting Python tests in general is a large, error-prone surface. The phase asks for a deliberately small subset.
- Decision: A module is a test file only when its filename starts with `test_` or ends with `_test.py` (directory names are deliberately not used). From such files, two shapes are mined: `assert <call> <op> <expected>` where one side is a direct `Call` and the operator is a single comparison (the reversed form `assert <expected> <op> <call>` is normalized only when the operator inversion is safe), and `with pytest.raises(<Exc>):` whose body is exactly one expression statement containing one direct call. Everything else in a test file (chained comparisons, compound `with` bodies, fixtures, parametrization, plain truthiness asserts) is ignored.
- Why: A filename rule is deterministic and cannot silently reinterpret production modules that merely live under a `tests/` directory. Recognizing `pytest.raises` as `Attribute(value=Name('pytest'), attr='raises')` is purely syntactic and never imports pytest. Ignoring chained comparisons keeps one comparison per expectation, which is what the resolution and normalization rules are defined for.
- Alternatives considered: also mining `unittest` assertion families and doctests (explicitly out of scope); treating any file under a `tests/` directory as a test (would classify non-test helpers as tests); mining `assert <call>` with no comparison (no expected outcome exists, so nothing verifiable could be recorded).
- Consequences: Test files still receive structural and semantic analysis like any other file; only oracle mining treats them specially. Unmined test idioms are a documented limitation rather than silent gaps.
- Files: src/edgehunter/oracle/test_expectations.py, tests/test_oracle_test_expectations.py

### D-026: Conservative target resolution for mined test expectations

- Date / phase / commit: 2026-10-08, Phase 3 (Structural Risk Scoring + Oracle / Property Mining), 12d82df
- Context: A mined expectation is only useful attached to a target when the callee provably refers to exactly one production target. Guessing would attach a false oracle to real code.
- Decision: Resolution uses a repository-wide index of simple callable name to qualified names. A bare callee name resolving to exactly one target becomes `RESOLVED` with that target; two or more matches become `AMBIGUOUS` with `target=None`; no match becomes `UNRESOLVED` with "no target with this name". A callee whose text contains a dot (a receiver call such as `service.calculate`, or a chained call such as `Account(100).withdraw`) is always `UNRESOLVED` with the reason "receiver resolution not implemented". Unresolved and ambiguous expectations are still reported; only `RESOLVED` ones contribute to a target's oracle support.
- Why: Attachment drives oracle support, so a wrong guess would claim a target has strong evidence it does not have. Explicit ambiguity is more useful than silence: it tells a future phase exactly which expectations would become resolvable with import resolution. Not attempting receiver or import resolution avoids the whole class of import-time side effects.
- Alternatives considered: attaching ambiguous expectations to every candidate target (over-claims support on all of them); resolving dotted calls by guessing the receiver is a class or module (unsound); dropping unresolved evidence (loses information for no benefit).
- Consequences: Real repositories report many unresolved expectations; a scan of this repository resolved 53 and left 24 unresolved and 5 ambiguous, which is the rule working as designed. A later repository-modeling phase can add resolution without changing the evidence model.
- Files: src/edgehunter/oracle/test_expectations.py, src/edgehunter/oracle/repository.py, tests/test_oracle_test_expectations.py, tests/test_pipeline.py

### D-029: A closed semantic action vocabulary with two recorded origins

- Date / phase / commit: 2026-10-08, Phase 4 (Semantic Action Engine + Input Materialization), 1500640
- Context: Phase 2 produces symbolic `BoundaryCandidate` regions but deliberately stops before choosing an input, because choosing one requires knowing a parameter's type. Phase 4 has to close that gap without reopening the type-resolution question and without giving itself an open-ended "generate something interesting" escape hatch.
- Decision: Add a `generation` package whose action vocabulary is the closed enum `SemanticActionKind` with twelve members. Ten correspond one-to-one with all ten `BoundaryKind` values via the total mapping `BOUNDARY_ACTIONS` (`ZERO`→`SET_ZERO`, `NAN`→`USE_NAN`, `JUST_BELOW`→`JUST_BELOW_BOUNDARY`, and so on), so no mined candidate can be silently dropped. The remaining two, `EMPTY_COLLECTION` and `SINGLETON_COLLECTION`, are collection-shaped and have no boundary counterpart. Every action records an `ActionOrigin`: `BOUNDARY` when a mined candidate justified it, `ANNOTATION` when the parameter's declared annotation did. `ACTION_KIND_ORDER` fixes the presentation order as relational, then numeric, then collection, so output never depends on enum declaration order.
- Why: A closed vocabulary is the only way to answer "what could EdgeHunter possibly propose?" without reading the implementation, which is the property that makes a later search policy auditable. Making the mapping from `BoundaryKind` total means the action list can be checked against the boundary list for equality. Keeping two distinct origins on the record means a reader can always tell whether an action came from a comparison in the source or from a declaration in a signature, and those carry different confidence.
- Alternatives considered: a free-form action string per target (unbounded, unauditable, and the "small model" the project rejects); one action per parameter with a list of values (fuses the action and the value, so provenance per value is lost); reusing `BoundaryKind` unchanged as the action type (leaves collections unrepresentable, since `BoundaryKind` has no collection member and Phase 2 has no collection evidence).
- Consequences: Action count equals boundary count plus annotation-derived collection actions; `test_boundary_kind_maps_onto_every_action_kind` asserts the mapping is total and injective, and `test_pipeline_produces_structure_semantics_oracles_risk_and_actions` asserts action count equals boundary count on a fixture with no collection annotations. Scanning EdgeHunter itself yields 19 actions from 19 boundary candidates and zero collection actions, because the package annotates with `Path`/`str`/`int` and subscripted generics rather than bare `list`/`dict`.

### D-030: Applicability comes from Phase 2's exact-match annotation rule, extended only to bare builtin collections

- Date / phase / commit: 2026-10-08, Phase 4 (Semantic Action Engine + Input Materialization), 1500640
- Context: Boundary mining restricts generic numeric candidates to a parameter annotated exactly `int` or `float`. Phase 4 needs an equally defensible rule for when a collection action applies, and the tempting answer — parse the annotation to understand `list[int]` or `Optional[int]` — reintroduces exactly the annotation resolution the project has refused since Phase 1.
- Decision: Add `AnnotationCategory` with five recognized builtin collection spellings (`list`, `tuple`, `dict`, `set`, `frozenset`) and `UNKNOWN`, matched by exact string against `ParameterInfo.annotation` using the same `.get(annotation, default)` pattern Phase 2 uses for `int`/`float`. `classify_annotation()` returns `UNKNOWN` for `None`, for any other name, and for every subscripted or parameterized spelling such as `list[int]`, `dict[str, int]`, and `Optional[int]`. Annotation-derived actions are restricted to the shared `SINGLE_VALUE_PARAMETER_KINDS` buckets, so `*args` and `**kwargs` never receive a generic action. An untyped or unrecognized parameter is not excluded from the whole phase: it still receives actions derived from its own comparisons.
- Why: Reusing the exact-match rule rather than writing a new, looser matcher keeps one consistent and conservative posture toward annotations across phases, and means an unrecognized annotation cannot silently produce a value of the wrong shape. Leaving `*args`/`**kwargs` alone is consistent with `SINGLE_VALUE_PARAMETER_KINDS`: one action cannot describe an unknown number of values. The "untyped still gets relational actions" rule is what keeps the phase useful on real code, where most parameters are unannotated.
- Alternatives considered: matching on the origin name before `[` so `list[int]` counts as a list (silently discards the element type, and the empty/singleton values would then claim to be `int`-typed); supporting `Optional[int]` by string surgery (a second, ad-hoc annotation parser with its own failure modes); resolving annotations through `typing.get_type_hints` (imports the analyzed module, which D-011 forbids outright).
- Consequences: On a typical modern codebase most `list`/`dict` annotations are subscripted and therefore unrecognized, so this phase produces few collection actions there. `test_unrecognized_annotations_get_no_generic_action` and `test_unrecognized_annotations_never_trigger_construction` lock this in as intended behavior rather than a gap. Recognizing `Sequence`/`Iterable`/`MutableMapping` was considered and rejected because the correct empty literal for an abstract base class is a judgement call, not a fact.
- Files: src/edgehunter/generation/actions.py, src/edgehunter/generation/models.py, src/edgehunter/scanner/models.py, tests/test_generation_actions.py, tests/test_safety.py

### D-031: Three-state materialization, with numeric neighbours computed from literals and names left symbolic

- Date / phase / commit: 2026-10-08, Phase 4 (Semantic Action Engine + Input Materialization), 1500640
- Context: A boundary candidate names a region, not a value. Turning "just above 100" into a usable input needs the reference's type, and turning "just above `self.balance`" into one would need that balance's runtime value, which this phase does not have.
- Decision: Give every action a `MaterializationStatus` of `CONCRETE`, `SYMBOLIC`, or `UNSUPPORTED`, and render values as source text only. For a literal reference, the analysis layer's existing `ConstantKind` classification (recovered from the target's already-mined comparisons via `reference_constant_kinds()`, no re-parse) selects the rule: integer literals use exact neighbours (`9`, `10`, `11`), float literals use `math.nextafter` and are rendered with `repr`, and every other literal kind can be matched exactly but not stepped. For a name or attribute reference, `AT_BOUNDARY` stays `SYMBOLIC` naming the reference, and the below/above forms stay `SYMBOLIC` too because stepping away from an unknown value would mean inventing one. Literal text is parsed with `int`/`float`, never `eval` or `ast.literal_eval`; a parse failure becomes `UNSUPPORTED` rather than a guess. Each action keeps two separate reasons: `reason` for why the action was proposed and `materialization_reason` for how the value was written down.
- Why: Splitting the three states keeps "we know the value" distinct from "we know the shape but not the value" distinct from "there is no value here", which a single boolean would flatten into the worst case. Rendering floats with `repr` and stepping with `nextafter` is the only way to produce a genuinely adjacent representable float; writing `0.5 - 0.1` would invent a value that is not adjacent. Splitting the two reasons matters because a user looking at an `unsupported` action needs to know it was *considered and rejected*, not silently dropped.
- Alternatives considered: emitting `0.5 - 1e-9` as an epsilon step (not adjacent, and silently wrong near a boundary); using `decimal` or `fractions` for exact rational neighbours (changes the value's type, which a `float` parameter may not accept); marking symbolic results `UNSUPPORTED` instead (loses the fact that a concrete value exists once the reference is known, which is exactly what a later harness phase can supply); reusing the comparison's rendered syntax as the value for `AT_BOUNDARY` (that is a reference, not a value).
- Consequences: `just_below 0.5` materializes to the exact literal `0.49999999999999994`, asserted in `test_float_neighbour_uses_the_adjacent_representable_value`. Stepping around a `complex` literal is `UNSUPPORTED`, which is the reachable path exercised by `test_unsupported_action_is_not_a_candidate_case`. Signed numeric literals such as `-1` never appear as references because Phase 2 requires `simple` references and a `UnaryOp` is not simple, so no sign handling is needed here. `MaterializationStatus.UNSUPPORTED` for a generic numeric kind with no rendering in the declared type is defensive; Phase 2's annotation restriction means it is not normally reached.
- Files: src/edgehunter/generation/materialize.py, src/edgehunter/generation/models.py, src/edgehunter/generation/actions.py, tests/test_generation_materialize.py

### D-032: Candidate cases carry one action, never invent a sibling value, and report what they leave uncovered

- Date / phase / commit: 2026-10-08, Phase 4 (Semantic Action Engine + Input Materialization), 1500640
- Context: The project's whole premise is a meaningful counterexample, but a call like `discount(amount, rate)` needs a value for both parameters. Filling in the untouched ones means inventing a baseline, and an invented baseline silently decides which bugs the search can find.
- Decision: A `CandidateCase` holds exactly one `SemanticAction` and is never a combination, so no Cartesian product of actions is possible. A case never supplies a value for any other parameter. Instead it records `missing_parameters` — the target's required parameters it does not cover — and a `CandidateCompleteness` of `COMPLETE` (concrete value, nothing required left over), `PARTIAL` (concrete value, other required parameters uncovered), or `SYMBOLIC` (the value still depends on a name). A required parameter is one with no default, not `*args`/`**kwargs`, and not a method's `self`/`cls` receiver. Only `CONCRETE` and `SYMBOLIC` actions become cases; an `UNSUPPORTED` action stays in the action list with its reason but is not a candidate, because there is nothing to hand a runner.
- Why: Naming the missing parameters gives a later harness phase exactly the information it needs to build the rest of the call, and doing it in this phase means the choice is visible in static output rather than deferred to whoever writes the executor. Making `SYMBOLIC` a case rather than dropping it preserves the region for later resolution, while excluding `UNSUPPORTED` keeps the case list free of entries that could never run. Reusing the existing receiver rule means risk scoring and candidate generation agree about what counts as user input.
- Alternatives considered: emitting one case per combination of actions (combinatorial blow-up and invents a baseline for every extra parameter); silently omitting incomplete cases (loses the target entirely); inventing `0`/`None` defaults for uncovered parameters (the exact fabrication this phase exists to avoid); reporting completeness as a percentage (nothing here is calibrated, per D-023's reasoning).
- Consequences: Most cases on a multi-parameter target are `PARTIAL`, which is honest rather than a defect: the ratio `case_count == action_count - unsupported_action_count` and the three-way count split are asserted in `test_counts_add_up`. Scanning EdgeHunter itself gives 12 partial and 7 symbolic cases and zero complete ones, since its annotated parameters are mostly single-parameter targets reached through helpers whose other parameters are unannotated.
- Files: src/edgehunter/generation/repository.py, src/edgehunter/generation/models.py, src/edgehunter/generation/actions.py, tests/test_generation_cases.py

### D-033: Annotation-driven collection values use a documented `None` element placeholder

- Date / phase / commit: 2026-10-08, Phase 4 (Semantic Action Engine + Input Materialization), 1500640
- Context: `EMPTY_COLLECTION` is unambiguous, but `SINGLETON_COLLECTION` needs a one-element value and a bare `list` or `dict` annotation does not say what the element type is.
- Decision: Materialize an empty value per category (`[]`, `()`, `{}`, `set()`, `frozenset()`) and a singleton with a `None` placeholder element (`[None]`, `(None,)`, `{None: None}`, `{None}`, `frozenset({None})`). The mapping keys use `None` rather than an invented string such as `"key"`, so nothing semantic is fabricated. - Consequences: The emitted text is always syntactically valid Python, which `test_materialized_values_are_source_text_not_executed_objects` and `test_every_recognized_collection_has_an_empty_value` pin down. A target that rejects the `None` element is exercising its validation path, which is a legitimate finding rather than a wasted case.

### D-036: One canonical static annotation-shape interpreter, built during the single parse

- Date / phase / commit: 2026-10-08, Phase 5 (Static Annotation Shapes + Safe Baselines + Strategy Planning), 52fb551
- Context: Phase 4 matched annotation *text* exactly against `int`, `float`, and five bare collection names, which meant `list[int]` and `int | None` produced nothing. Fixing that by re-parsing annotation strings would have broken the one-read/one-parse property, and fixing it in several places would have produced several disagreeing interpreters. A further problem: the annotation is the one piece of a signature that is genuine *syntax* rather than a value, so it is the only place where structure is available without execution.
- Decision: Add `scanner/annotations.py` with `AnnotationKind` (`UNKNOWN`, `INT`, `FLOAT`, `BOOL`, `STR`, `NONE`, `LIST`, `TUPLE`, `SET`, `DICT`, `UNION`) and an immutable `StaticAnnotation(kind, rendered, nullable, element, key, value, variadic)`. `build_static_annotation(node)` interprets the `ast.expr` that is **already** available in `scanner/targets._build_parameter`, and the result is stored on `ParameterInfo.shape`. No extra read and no extra `ast.parse` is introduced: `ast.arg.annotation` is part of the single existing parse, and the whole repository still costs one read plus one parse per file. Recognized: bare `int`/`float`/`bool`/`str`/`None`; bare and subscripted `list`/`tuple`/`set`/`dict`; `tuple[T, ...]` (variadic) and `tuple[T]`; `List[...]`/`Tuple[...]`/`Set[...]`/`Dict[...]`/`Optional[...]`/`Union[...]`; the `typing.`-prefixed spellings of those; and PEP 604 unions. Nullability is a separate `nullable` flag rather than a separate kind, so `int | None` is `kind=INT, nullable=True` and every `INT` rule still applies, while `description` renders it as `OPTIONAL[INT]`. One recognized type plus `None` is the supported union form; any other multi-type union becomes `UNION`, which generates no values. `AnnotationCategory` and `classify_annotation()` are removed: the shape replaces them.
- Why: Building the shape from the AST node the scanner already holds is the only approach that both satisfies modern annotation syntax and keeps D-015's single-parse invariant — no second parser exists anywhere in the project. `nullable` as a flag rather than a kind means a nullable integer is not a special case: the numeric boundary set, the `0` baseline, and the strategy set all apply unchanged, which is what a caller actually means. Keeping the rendered text on the shape means display is unaffected and `ParameterInfo.annotation` still works for backwards compatibility.
- Alternatives considered: re-parsing the annotation string with `ast.parse(mode='eval')` (a second parse per parameter, explicitly forbidden by the phase, and it would silently change the "one parse per file" claim); string matching on `Optional[`/`[`/`|` (a second, ad-hoc grammar with its own failure modes and no access to nesting); resolving annotations with `typing.get_type_hints` (imports the analyzed module, forbidden since D-011). Recognizing `Sequence`/`Iterable`/`Mapping`/`MutableMapping` was rejected: the correct concrete empty value for an abstract base class is a judgement call, not a syntactic fact. `frozenset` was dropped rather than given a new kind: `set()` is not a `frozenset`, and emitting one would be a wrong-typed value.
- Consequences: `test_pep604_nullable_annotation_gets_no_generic_candidates`-style expectations from Phase 2 are superseded: `int | None`, `Optional[int]`, and `list[int]` now receive actions, which is why `test_nullable_annotation_gets_generic_candidates`, `test_pep604_nullable_annotation_gets_generic_candidates`, `test_unrecognized_annotation_gets_no_generic_candidates`, and `test_bool_annotation_is_not_numeric` were added to `tests/test_boundaries.py`. `bool` is a distinct kind and therefore never receives numeric candidates, preserving D-016's bool-before-int discipline. Forward references (`"User"`), user aliases (`MyInt = int`), `Annotated`, `Literal`, `NewType`, `TypeVar`, `Protocol`, `Callable`, and any annotation that is a call expression all stay `UNKNOWN`, and the rendered text is retained.
- Supersedes: D-030 (exact-match annotation categories) for applicability; extends D-017's numeric-candidate rule from exact annotation text to the annotation shape

### D-037: Unknown element types no longer produce a `None` placeholder (supersedes D-033)

- Date / phase / commit: 2026-10-08, Phase 5 (Static Annotation Shapes + Safe Baselines + Strategy Planning), 52fb551
- Context: Phase 4 materialized `SINGLETON_COLLECTION` for an unknown element type by inserting `None`: `[None]`, `{None: None}`, `frozenset({None})`. That is a fabricated value. A target annotated `items: list` may well reject `None`, so the case would fail for a reason that has nothing to do with the behaviour under test, and a future failure could be misattributed to the adversarial action.
- Decision: A singleton or repeated-element collection is materialized only when the element shape yields a trustworthy baseline. When the element shape is unknown, absent, unhashable, or otherwise unsupported, the action is still proposed (the size-one and repeated-element *regions* are real and worth searching) but its materialization is `UNSUPPORTED` with a reason that says no trustworthy element baseline exists. `EMPTY_COLLECTION` remains unconditionally available for every recognized container kind, because an empty container needs no element knowledge. Known primitives give `list[int]` → `[0]`, `list[float]` → `[0.0]`, `list[str]` → `[""]`, `list[bool]` → `[False]`, `tuple[str, ...]` → `("",)`, `set[bool]` → `{False}`, `dict[str, int]` → `{"": 0}`. A nullable element prefers its non-null baseline, so `list[int | None]` yields `[0]`. A nested container element uses that element's own baseline rather than recursing, so `list[list[int]]` yields `[[]]`. An unhashable element (`set[list[int]]`) is `UNSUPPORTED` because `{[0]}` is not valid Python. `None` is proposed only where the annotation itself supports it, via the new `SET_NONE` action for a nullable shape.
- Why: "Unknown does not mean nullable" is the whole point. Keeping the action while withholding the value preserves the action-space semantics — the region stays visible in the action list with the reason it could not be written down — without handing a later executor a value that is guaranteed to be rejected. Refusing to fabricate is what makes the deterministic baseline trustworthy enough to benchmark against.
- Alternatives considered: omitting `SINGLETON_COLLECTION` entirely for unknown elements (loses the size-one region, which is a classic source of off-by-one and indexing bugs); emitting a placeholder token such as `[<element>]` (not valid Python, so it could never be executed); guessing `0`/`""` for an unknown element (silently claims a type EdgeHunter does not know, which is the same error as `None`).
- Consequences: A bare `list` now produces exactly one usable candidate, `[]`. `test_bare_collection_gets_no_fabricated_singleton`, `test_unknown_element_type_never_fabricates_a_placeholder`, `test_unknown_element_shape_never_fabricates_a_placeholder`, `test_unhashable_element_is_not_rendered_as_a_set`, `test_nullable_element_prefers_the_non_null_baseline`, and `test_scan_never_fabricates_a_none_placeholder` lock this in. Two Phase 4 tests that asserted the placeholder (`test_materialized_values_are_source_text_not_executed_objects`, `test_unrecognized_annotations_never_trigger_construction`) were rewritten to assert the absence of `[None]`.
- Supersedes: D-033

- Date / phase / commit: 2026-10-08, Phase 5 (Static Annotation Shapes + Safe Baselines + Strategy Planning), 52fb551
- Context: D-029 established a closed vocabulary of twelve actions. Phase 5 needs two more regions that D-029's list could not express, and both are annotation-driven rather than boundary-driven.
- Decision: `SemanticActionKind` gains `SET_NONE` and `DUPLICATE_ELEMENT_COLLECTION`, giving fourteen members. `BOUNDARY_ACTIONS` is unchanged and still maps all ten `BoundaryKind` values one-to-one onto ten actions, so the boundary-to-action mapping stays total and injective. `SET_NONE` is proposed for any parameter whose shape `is_nullable`, including a bare `None` annotation, and is the only way `None` reaches a materialized value. `DUPLICATE_ELEMENT_COLLECTION` is proposed for `list` and `tuple` only, because a repeated element is meaningless in a `set` and would render invalidly. ### D-039: Safe baseline synthesis with explicit provenance and a fixed precedence

- Date / phase / commit: 2026-10-08, Phase 5 (Static Annotation Shapes + Safe Baselines + Strategy Planning), 52fb551
- Context: An invocation plan needs values for arguments it has no adversarial intent for. Choosing them is where a static analysis most easily starts lying: `0` is not a valid integer in general, and calling it one would make a later failure look like a finding when it is really a filler artefact.
- Decision: Add `generation/baselines.py` with `BaselineSource` (`STATIC_TYPE`, `EXISTING_TEST`, `DECLARED_DEFAULT`, `DEPENDENCY`) and an immutable `BaselineValue(source, value_text, literal_kind, reason)`. `baseline_for(shape)` returns the simplest statically constructible value for a recognized shape: `int`→`0`, `float`→`0.0`, `bool`→`False`, `str`→`""`, `None`→`None`, and the empty container for each container kind; a nullable shape yields its **non-null** baseline; `UNKNOWN` and multi-type `UNION` yield `None`. `BaselineValue.reason` states that the value is a filler and not a claim that the target accepts it. Filler precedence is fixed: an observed existing-test literal, then a dependency baseline, then a declared default (the parameter is simply omitted), then the static type baseline, then nothing. Nothing is instantiated: there is no `User()` and no `None` fallback for an unrecognized type.
- Why: Naming the source on every value is what will later let a failure be attributed to the adversarial action rather than to the filler, which is the phase's stated goal of preserving causal attribution. Making `None` the answer for an unknown type is precisely the fabrication D-037 removed one layer up, so the baseline layer refuses it too. Choosing the non-null baseline for a nullable parameter keeps `None` an adversarial choice (`SET_NONE`) rather than an automatic filler, so the interesting region is still searched.
- Alternatives considered: reusing `Hypothesis.strategies.just()` semantics as the filler (a library dependency for one constant, and it would blur the boundary between a planned value and a generated one); defaulting an unrecognized parameter to `None` (invents a value for a type EdgeHunter does not understand, and silently turns every unknown into a null check); leaving unknown parameters to the harness phase (deferring the fabrication instead of preventing it).
- Consequences: A nullable `int` parameter is filled with `0` unless it has a declared default, which is then omitted instead — `test_nullable_argument_without_default_gets_a_non_null_baseline` and `test_nullable_argument_with_default_is_omitted` pin both halves of that rule. Empty containers need no element knowledge, so a bare `list` still has a usable baseline even though it has no usable singleton element.
- Files: src/edgehunter/generation/baselines.py, src/edgehunter/generation/invocation.py, tests/test_invocation.py

### D-040: Typed invocation plans with one adversarial action, honest completeness, and an explicit receiver requirement

- Date / phase / commit: 2026-10-08, Phase 5 (Static Annotation Shapes + Safe Baselines + Strategy Planning), 52fb551
- Context: D-032 deliberately left most candidate cases `PARTIAL`, because filling the untouched arguments would invent a baseline. That was correct for the action layer but leaves the cases unrunnable, and Phase 4's `CandidateCompleteness` can no longer express the distinctions that now matter — a method that needs a constructed receiver is not the same as a plain function with every argument filled.
- Decision: `generation/invocation.py` adds `InvocationPlan`, `ArgumentAssignment`, `AssignmentOrigin` (`ADVERSARIAL_ACTION`, `STATIC_TYPE_BASELINE`, `EXISTING_TEST_BASELINE`, `DECLARED_DEFAULT`, `DEPENDENCY_BASELINE`), `ArgumentPlacement` (`POSITIONAL_ONLY`, `POSITIONAL`, `KEYWORD`, `OMITTED`, `VAR_POSITIONAL`, `VAR_KEYWORD`), and `InvocationStatus` (`COMPLETE_FUNCTION`, `NEEDS_RECEIVER`, `PARTIAL_ARGUMENTS`, `SYMBOLIC_DEPENDENCY`). Planning sits **above** the candidate layer rather than replacing it: one plan per `CandidateCase`, so `plan_count == case_count` always holds. Every plan has exactly one `ADVERSARIAL_ACTION` assignment; every other entry is a filler and records which kind. Placement comes from the Phase 1 `ParameterKind`, and positional/keyword subsets are derived properties of that one ordered tuple rather than two independently kept lists. A parameter with a declared default is recorded as `DECLARED_DEFAULT` with `placement=OMITTED` and no value, which satisfies completeness without evaluating the default. A method's `self`/`cls` is never synthesized: it sets `requires_receiver` and forces `NEEDS_RECEIVER`, so a method plan is never reported as locally invocable. `*args`/`**kwargs` receive no assignment and do not affect completeness. Status precedence is most-fundamental-gap-first: `SYMBOLIC_DEPENDENCY`, then `PARTIAL_ARGUMENTS`, then `NEEDS_RECEIVER`, then `COMPLETE_FUNCTION`.
- Why: Keeping exactly one adversarial entry is what makes a later failure attributable: `x = -1 [adversarial_action]` next to `name = "" [static_type_baseline]` says the interesting thing is the `-1`. Placing plans above cases keeps D-032's single-action abstraction auditable rather than dissolving it into a bag of assignments. Using a distinct `NEEDS_RECEIVER` status, instead of reusing Phase 4's vocabulary, is what stops EdgeHunter from claiming a method is ready to run when no instance exists.

### D-041: Symbolic parameter references resolve through baselines, reusing the one adjacency materializer

- Date / phase / commit: 2026-10-08, Phase 5 (Static Annotation Shapes + Safe Baselines + Strategy Planning), 52fb551
- Context: For `if x <= limit` with `limit: int`, D-031 correctly refused to invent a neighbour of `limit` because its value is unknown. Phase 5 does have a trustworthy baseline for `limit`, so the region becomes reachable: baseline `limit`, compute the neighbour of that baseline, and record that `x` depends on a baseline-filled `limit`.
- Decision: When the primary action's status is `SYMBOLIC` and its `symbolic_text` is a bare identifier naming **another declared parameter of the same target** whose shape has a baseline, `_resolve_symbolic_dependency()` baselines that parameter and re-runs the *same* `materialize_relational()` used for literal references, converting the action to `CONCRETE`. The referenced parameter's assignment records origin `DEPENDENCY_BASELINE`. Resolution is refused when the reference is dotted (`self.limit`), names no parameter, is the receiver, has no baseline, has a shape with no literal form, or yields a non-concrete result — in which case the plan stays `SYMBOLIC_DEPENDENCY`. Keeping the dependency explicit means the resulting plan is still explainable: `x = 1 [adversarial_action]` and `limit = 0 [dependency_baseline]`.

### D-042: Literal arguments from resolved existing tests may serve as baselines

- Date / phase / commit: 2026-10-08, Phase 5 (Static Annotation Shapes + Safe Baselines + Strategy Planning), 52fb551
- Context: Phase 3 already mines expectations such as `assert add(1, 2) == 3`. Those arguments are inputs a repository author actually chose, which is stronger evidence than a synthesized generic baseline, and the phase lists them as a recommended baseline source.
- Decision: `TestExpectationCandidate` gains `literal_arguments: tuple[str, ...]`, populated during mining from the `ast.Call` that is already in hand. ### D-045: Docker is the only execution backend, and there is deliberately no host fallback

- Date / phase / commit: 2026-10-09, Phase 6A (Isolated Execution Backend), 89865f7
- Context: Phase 6A must execute untrusted target code without importing or invoking it on the host. A "try Docker, otherwise run locally" design would make the safe path optional, which is precisely the failure mode the phase exists to prevent: the local path would be taken silently whenever Docker was slow, missing, or misconfigured.
- Decision: Add `execution/docker.py` as the only module permitted to start a host process, and it may only start the `docker` CLI. `docker_available()` returns a truthful `(bool, detail)` after checking for the CLI, that the daemon answers, and that the server `OSType` is `linux`. When it returns false, `execute_target` produces a report with `SandboxState.UNAVAILABLE` and zero results. There is no in-process interpreter, no `exec`, and no alternative runner.
- Why: A security boundary that has a fallback is not a boundary, because the fallback is exercised exactly when the boundary is unavailable. Refusing to run is a reportable outcome, not an error to be papered over.
- Alternatives considered: running target code in a host subprocess under a temporary directory (a subprocess shares the user's filesystem, credentials, and network); using `multiprocessing` or `subprocess` with a restricted environment (no filesystem, network, or capability isolation on any supported platform); falling back to a "no sandbox" mode with a warning (silently downgrades the guarantee the user asked for).
- Consequences: `test_missing_docker_cli_is_reported_as_unavailable`, `test_unreachable_daemon_is_reported_as_unavailable`, `test_non_linux_daemon_is_refused`, and `test_linux_daemon_is_accepted` pin the availability contract. `test_execution_package_never_starts_a_process` in tests/test_execution_safety.py asserts structurally that only `subprocess.*` calls exist under `execution/`.
- Files: src/edgehunter/execution/docker.py, src/edgehunter/execution/repository.py, tests/test_execution_docker.py, tests/test_execution_safety.py

### D-046: Values cross the boundary as strict typed JSON, and rendered literals are recognized by an AST whitelist

- Date / phase / commit: 2026-10-09, Phase 6A (Isolated Execution Backend), 89865f7
- Context: Phase 5 plans carry values as rendered source text such as `-1`, `0.0`, or `[1, 2]`. Turning that into Python must not mean calling `eval`, and the protocol must survive JSON's lack of a float type for `nan`/`inf` and its treatment of sets and tuples.
- Decision: `execution/codec.py` defines `ValueKind` (`INTEGER`, `FLOAT`, `BOOLEAN`, `STRING`, `NONE`, `LIST`, `TUPLE`, `SET`, `MAPPING`) and a versioned JSON document. `recognize_literal()` parses the rendered text with `ast.parse(..., mode="eval")` and accepts only literal nodes; a `Call`, `Name`, `Attribute`, `BinOp`, or comprehension raises `ProtocolError`. Special floats travel as the strings `nan`, `inf`, `-inf`, and `-0.0` is preserved. Sets are ordered by canonical JSON text so encoding is deterministic. Documents are capped at 64 KiB with depth 4, 100 collection items, 100 mapping entries, 4096-character strings, and an 8192-character rendered literal. Unknown keys in any typed value are rejected.
- Why: An AST whitelist is the narrowest thing that accepts the literals the planner already produces while being unable to reach an interpreter, so the protocol cannot be talked into executing code. Canonical ordering for sets is what makes a result reproducible and testable.
- Alternatives considered: `ast.literal_eval` (it accepts far more node types than needed and its accepted set is an implementation detail rather than a reviewed policy); `eval` in a restricted namespace (still an interpreter; a single oversight is code execution); encoding values as `repr` strings (a target-defined `__repr__` would run on the worker); a non-JSON pickle protocol (object deserialization, which the phase forbids outright).
- Consequences: 53 tests in tests/test_execution_codec.py cover the wire format, the limits, and the refusal of every non-literal node type. `test_no_pickle_or_object_deserialization_anywhere` asserts no module imports a deserializer.
- Files: src/edgehunter/execution/codec.py, tests/test_execution_codec.py, tests/test_execution_safety.py

### D-047: The result travels in a file guarded by a nonce, never on stdout

- Date / phase / commit: 2026-10-09, Phase 6A (Isolated Execution Backend), 89865f7
- Context: Target code can write to file descriptor 1 at will. A protocol on stdout would therefore be forgeable by the target: it could print a fabricated successful result, or corrupt a real one mid-flight.
- Decision: The worker writes exactly one result document to `/output/result.json` and nothing else. While the target runs, file descriptors 1 and 2 are redirected to `/dev/null`. Every request carries a fresh unguessable `nonce`; the host compares it to the returned document and reports a nonce mismatch as `PROTOCOL_ERROR`. The host also requires `execution_id` to match and rejects any unknown top-level key. A missing result document is `WORKER_FAILURE`, never an implicit pass.
- Why: The channel that untrusted code can write to is exactly the channel the protocol must not use. The nonce makes the binding between one request and one response checkable instead of assumed.
- Alternatives considered: encoding the result on a dedicated file descriptor passed to the worker (unnecessary indirection; a file in a directory only the result can write to achieves the same isolation); trusting any well-formed document from the container (a stale file from a previous run would be indistinguishable); exiting non-zero to signal the outcome (loses the structured detail and collapses distinct failures into one code).
- Consequences: `test_result_documents_never_reach_the_container_stdout` runs a target that calls `os.write(1, ...)` and asserts the protocol survives. `TestHReadOnlyStaging` and the refusal tests depend on the same rule.
- Files: src/edgehunter/runtime/worker.py, src/edgehunter/execution/repository.py, tests/test_execution_integration.py

### D-048: Return values are described by exact built-in type checks, and anything else is reported opaque

- Date / phase / commit: 2026-10-09, Phase 6A (Isolated Execution Backend), 89865f7
- Context: Recording a return value is convenient, but every serialization route for a target-defined object runs target code: `repr` may be overridden, `pickle` executes `__reduce__`, and `__str__` may raise or block. A hostile `__repr__` would therefore be executing inside the sandbox on the recording path.
- Decision: `_encode_value` uses `type(value) is X` for `bool`, `int`, `float`, `str`, `list`, `tuple`, `set`, and `dict` — exact checks, never `isinstance`, so a subclass with a custom `__repr__` is not silently encoded as its base. A set containing an unhashable-shaped element is refused. Anything else yields `{"outcome": "returned", "opaque_return": "returned <TypeName> (not representable)"}`. Exception types and messages are read through `type(exc).__name__` and `str(exc)`, both clipped.
- Why: Exact type checks mean the recording path only ever touches built-ins whose behaviour is known, so no target-defined code runs to produce a report about a target-defined object.
- Alternatives considered: `isinstance` (a subclass's `__repr__` would then be invoked when the value is rendered); `repr` with a length cap (still executes the override); `pickle` (explicitly forbidden, and unsafe even for a hostile-but-sandboxed target); reporting nothing at all for unrepresentable values (loses the information that *something* was returned).
- Consequences: `test_subclassed_int_is_not_encoded_as_an_integer`, `test_custom_object_is_reported_opaque_not_serialized`, and `test_set_of_unhashable_elements_is_refused` assert the refusals; the last two also assert that a hostile `__repr__`/`__reduce__` output never appears in the report.
- Files: src/edgehunter/runtime/worker.py, tests/test_execution_worker.py

### D-049: Arguments are assembled positionally only up to the first omitted default

- Date / phase / commit: 2026-10-09, Phase 6A (Isolated Execution Backend), 89865f7
- Context: D-040 records a defaulted parameter as `OMITTED` with no value. Turning that into a call has one non-obvious rule: once a positional-or-keyword parameter is skipped, every later positional-or-keyword parameter must also be passed by keyword, or the values shift by one position.
- Decision: `assemble_invocation()` walks the ordered parameter tuple once. A `POSITIONAL_ONLY` parameter is always passed positionally. The positional run continues while the placement is `POSITIONAL`; the first `OMITTED` parameter closes the positional run and everything after it is passed by keyword. Keyword-only parameters are always keywords. `VAR_POSITIONAL` and `VAR_KEYWORD` receive nothing. Any unsupported or unresolved value fails the whole plan closed rather than dropping the argument.
- Why: Getting this wrong would silently bind values to the wrong parameters, producing an observation about a call nobody made. Closing the positional run is the only arrangement that preserves each parameter's identity.
- Alternatives considered: filling omitted parameters with their declared defaults (requires evaluating them, which the phase forbids); passing every argument by keyword always (breaks `POSITIONAL_ONLY` parameters and any name-mangling or re-binding a call relies on); dropping the plan when any default is omitted (discards a large fraction of real targets for no safety gain).
- Consequences: `test_omitted_default_does_not_shift_the_next_positional`, `test_positional_only_parameter_is_passed_positionally`, `test_keyword_only_parameter_is_passed_by_keyword`, and `test_variadic_parameters_receive_nothing` cover the rules in tests/test_execution_assembly.py.
- Files: src/edgehunter/execution/assembly.py, tests/test_execution_assembly.py

### D-050: Output is bounded on both sides of the boundary, and the capture must never grow without limit

- Date / phase / commit: 2026-10-09, Phase 6A (Isolated Execution Backend), 89865f7
- Context: A flooding or looping target can produce unbounded output. The host must not grow its memory in response, and the worker's capture must be bounded at the moment of writing rather than after the fact.
- Decision: The worker redirects Python-level stdout/stderr into `_BoundedStream`, a sink that keeps at most 16 KiB and discards the excess as it arrives while always reporting a full write, so a target never sees a short write and never causes an accumulation. Native writes to file descriptors 1 and 2 go to `/dev/null`. On the host, `run_docker()` captures through temporary files read back under `MAX_CAPTURED_OUTPUT_BYTES` (64 KiB) rather than `capture_output=True`.
- Symptom: The first implementation used `io.StringIO` and truncated only after the invocation returned, so a target printing in a loop accumulated without limit for the whole run.
- Root cause: The bound was applied to the finished string instead of to the writer.
- Regression test: `test_flooding_never_grows_past_the_cap`, `test_output_beyond_the_cap_is_discarded`, and `TestDOutputFlood::test_flooding_output_is_truncated_not_unbounded`, which runs a real container printing 5,000 lines and asserts `stdout_truncated is True` and the captured size is within 16 KiB.
- Alternatives considered: keeping `StringIO` and clipping afterwards (the defect above); streaming output to the host and truncating there (moves unbounded memory to the host, which is the thing being protected); letting the container's memory limit absorb it (a cgroup OOM kill destroys the observation instead of recording it).
- Files: src/edgehunter/runtime/worker.py, src/edgehunter/execution/docker.py, tests/test_execution_worker.py, tests/test_execution_docker.py, tests/test_execution_integration.py

### D-051: Host-side process output is captured through files, not an in-memory pipe

- Date / phase / commit: 2026-10-09, Phase 6A (Isolated Execution Backend), 89865f7
- Context: `run_docker` originally used `subprocess.run(..., capture_output=True)`, which buffers both pipes entirely in host memory before returning. Target output does not reach those pipes, but a misbehaving or verbose Docker process would still be able to grow host memory for as long as the budget allowed.
- Decision: `_run_bounded()` redirects stdout and stderr to temporary files, closes them, and reads at most `MAX_CAPTURED_OUTPUT_BYTES` from each. `stdin` is `DEVNULL`. The timeout and the cleanup command behave as before.
- Symptom: The unbounded in-memory capture was found during the Phase 6A security review, not by a failing test.
- Root cause: `capture_output=True` was the convenient default, and the bound was only reasoned about for the worker side of the boundary.
- Regression test: `test_captured_output_is_bounded_even_for_a_flood` starts a real process that writes 500,000 bytes to both streams and asserts each captured stream is within the cap.
- Alternatives considered: reading the pipes incrementally (more code for the same guarantee); capping only the worker and accepting the host risk (the host is what the phase protects); limiting by process count instead of by bytes (does not bound a single noisy process).

### D-052: A target is identified by path and qualified name together, and ambiguity is refused

- Date / phase / commit: 2026-10-09, Phase 6A (Isolated Execution Backend), 89865f7
- Context: A qualified name is not unique. Two modules can each define `process`, and the earlier implementation kept the first match found while scanning, so `--target` could silently execute a different function than the user named.
- Decision: `--target` accepts `name` or `path::name`. Resolution collects every module that defines the name, applies the file hint when given, and requires exactly one match. Zero matches is an unknown target and more than one is `AMBIGUOUS_TARGET`; both name the candidate files and tell the user how to disambiguate. The resolved spec, including the file hint, is passed through to the execution layer so it resolves the identical identity rather than a bare name. Plan selection additionally matches on `relative_path`, so plans from a same-named function in another module are never mixed in.
- Symptom: `test_run_with_a_file_hint_resolves_the_ambiguity` failed with the ambiguity message even though `two.py::process` named exactly one definition.

- Alternatives considered: first match wins (silently runs the wrong function); last match wins (equally arbitrary); requiring a file hint always (adds friction for the common case where the name is unique).

A function returning `None` — very common — was therefore reported as `returned NoneType (not representable)`.
- Decision: `_encode_value` returns `TypedValue(kind=ValueKind.NONE)` for `None`, using a direct `is None` test rather than a `type()` comparison, and the opaque branch keeps its existing behaviour for genuinely unsupported types.

### D-057: Execution is reached only through an explicit opt-in, and a missing or duplicate result is never a pass

- Date / phase / commit: 2026-10-09, Phase 6A (Isolated Execution Backend), 89865f7
- Context: The static scanner must remain the default and must never execute anything, and a container that produced no readable result has told the user nothing about the target's behaviour.
- Decision: `edgehunter run` requires both `--target` and `--allow-execution`; without the flag it exits `3` before reading the repository. Exit codes are `0` when a run was observed, `2` for invalid input, and `3` for a refusal or unavailable backend; `1` is never used by `run`, so a run is never confused with the scanner's "issues found" code. Outcomes are `RETURNED`, `RAISED`, `TIMEOUT`, `IMPORT_FAILURE`, `TARGET_NOT_FOUND`, `PROTOCOL_ERROR`, and `WORKER_FAILURE`, each carrying its own detail. A missing result is `WORKER_FAILURE`; an unreadable or unknown-keyed document is `PROTOCOL_ERROR`.
- Why: Keeping `1` unused for `run` means a script can tell "the scanner found something" from "the run was refused" without parsing output, and it keeps an exception from ever reading as a defect.
- Alternatives considered: making `--allow-execution` a config-file setting (a hidden opt-out is not an opt-in); reusing exit code `1` for refusals (conflates "issues found" with "nothing ran"); treating a missing result as a timeout (invents an outcome the container never reported).
- Consequences: `test_run_without_opt_in_refuses`, `test_scan_never_consults_the_execution_backend`, `test_scan_exit_codes_are_unchanged`, and `test_static_analysis_entry_point_does_not_import_execution` pin the contract. The report prints "Oracle evaluation: not performed" and "Finding: none (this phase only observes)" so no output can be read as a bug claim.

### D-058: Six distinct oracle statuses, none of which is a synonym for another

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: Phase 6A recorded `RETURNED`, `RAISED`, `TIMEOUT`, and friends but deliberately judged nothing. The phase requires a vocabulary where "the target raised", "the sandbox would not start", "no oracle applies", and "an applicable oracle was contradicted" are all separately representable. A single boolean or a two-valued status would force at least one of those to be reported as another.
- Decision: `OracleStatus` has exactly six members: `MATCH`, `MISMATCH`, `NOT_APPLICABLE`, `INCONCLUSIVE`, `UNSUPPORTED`, `CONFLICTING_EVIDENCE`. `UNSUPPORTED` is separate from `MISMATCH` because a comparison EdgeHunter cannot perform must never read as a contradiction. `INCONCLUSIVE` is where every infrastructure failure lands. The execution status (`OutcomeKind`) remains a separate dimension and is never rewritten: `RAISED` with `MATCH` is a normal outcome, which is what makes `with pytest.raises(ValueError): validate(-1)` verifiable.
- Why: The whole value of this phase is that a reader can tell the difference between "the code disagrees with a recorded expectation" and "EdgeHunter could not find out". Merging the latter into the former would manufacture false bug reports, and merging them into silence would hide real ones. `UNSUPPORTED` earns its own member because the two failure directions need different remedies from a reader: one needs a broader comparison layer, the other needs a different invocation.
- Alternatives considered: a boolean `matches: bool | None` (three meanings in three states, and the reason is lost); reusing `OutcomeKind` with added members (conflates a fact about the run with a judgement about it); reporting `UNSUPPORTED` as `MISMATCH` with a caveat in prose (prose caveats are the thing this phase exists to replace).
- Consequences: `tests/test_evaluation_verify.py` pins every transition, including that all seven infrastructure outcomes leave an applicable oracle `INCONCLUSIVE`, and `test_evaluation_safety.py::test_every_finding_kind_avoids_severity_language` keeps the vocabulary itself honest.
- Files: src/edgehunter/evaluation/models.py, src/edgehunter/evaluation/evaluator.py, tests/test_evaluation_verify.py

### D-059: An expectation covers one exact invocation and is never generalized

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: `assert add(1, 2) == 3` records one example. The tempting generalization is `add(a, b) == a + b`, which would report a mismatch for almost every real input and make EdgeHunter useless as a bug finder. The phase's central rule is that an expectation applies to the exact recorded input only.
- Decision: Applicability requires (1) the same target identity, (2) every recorded argument being literal syntax, (3) no starred arguments, and (4) the same arguments bound to the same parameter names through the target's own signature. Both sides are reduced to a `BoundCall` of canonical `(parameter name, value text)` pairs and compared structurally. `add(1, 2)` and `add(a=1, b=2)` are recognized as the same invocation because Python binds both identically; `f(1)` and `f(1, 10)` are not, because equivalence would require evaluating a declared default, which this project never does. A non-literal argument, a starred argument, or an ambiguous callee is refused before any value is looked at.
- Why: Argument binding through the signature is the only comparison that is both sound and meaningful. Comparing rendered call text would treat `add(1, 2)` and `add(a=1, b=2)` as different examples and would fail to bind a literal recorded at position 1 to the right parameter when an earlier argument was non-literal. The refusal to normalize omitted defaults is a deliberate limit: it is the one normalization that would require executing an expression.
- Alternatives considered: matching on the raw call string (fails on equivalent call forms and on the shifted-literal case); normalizing positional and keyword forms by name without a signature (would bind `a=1` to a positional-only parameter, which Python rejects); evaluating declared defaults to complete the equivalence (evaluation, forbidden since D-011); partial matching on shared arguments (would report a mismatch when the oracle actually covered only part of the call).
- Consequences: Most real repository runs report `NOT_APPLICABLE` more often than `MISMATCH`, which is the rule working as designed. `test_different_inputs_do_not_inherit_the_recorded_expectation` in `tests/test_evaluation_integration.py` pins this against real Docker output, and `test_keyword_and_positional_forms_of_the_same_call_are_the_same_invocation` pins the equivalence that Python does guarantee.
- Files: src/edgehunter/evaluation/applicability.py, src/edgehunter/evaluation/models.py, tests/test_evaluation_applicability.py, tests/test_evaluation_integration.py

### D-060: Comparison uses Python's own operator semantics, and a refusal is never a contradiction

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: The evaluator must decide whether an observed value satisfies a recorded assertion. Inventing a stricter equality than Python's would report a mismatch for an assertion Python itself considers satisfied: `True == 1` is true in Python, so an integer `1` must satisfy `assert f(1) == True`. A target-defined object is worse still, because comparing it would invoke its `__eq__` on the host.
- Decision: `comparison/compare.py` applies the operator exactly as Python does, with no added type checks. Ordering that Python itself refuses with `TypeError` becomes `UNSUPPORTED`, never `MISMATCH`. Identity is supported only against the `None` singleton, because `x is y` between arbitrary values depends on identity EdgeHunter cannot observe and `==` is not a substitute. Every value reaching the comparison came from the Phase 6A codec's exact-type whitelist, so only built-ins are ever materialized and no user-defined comparison method can run. Observation identity for dedup and recheck comparison is rendered as canonical text, never decided by equality, so `NaN != NaN` and `-0.0 == 0.0` cannot collapse two distinguishable observations.
- Why: Using Python's semantics is the only defensible rule: the repository's own test suite is the authority on what its code should do, and that test passes or fails by Python's rules. The ordering cast is safe because Python's `TypeError` remains the real authority and is caught into `UNSUPPORTED`.
- Alternatives considered: a type-strict equality (breaks existing passing assertions); reporting a Python `TypeError` as a mismatch (claims the target violated an assertion it was never evaluated against); supporting identity between arbitrary values via `==` (silently changes what `is` means); dedup by equality or by raw JSON text (`NaN` breaks the first, durations and execution ids break the second).
- Consequences: `test_true_equals_one_so_the_assertion_is_satisfied` and `test_a_numeric_ordering_against_a_string_is_unsupported_not_a_mismatch` pin the two directions. `test_comparison_never_uses_string_matching_for_values` in the safety suite fails if anyone reintroduces a substring comparison, which would be a second equality rule that drifts.
- Files: src/edgehunter/evaluation/compare.py, src/edgehunter/evaluation/values.py, tests/test_evaluation_verify.py, tests/test_evaluation_safety.py

### D-061: Builtin exception identity uses the real hierarchy; custom exception identity is `INCONCLUSIVE`

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: Phase 6A records an exception by `type(exc).__name__` only. `pytest.raises(ValueError)` is satisfied by `UnicodeDecodeError` in Python, but a bare `PaymentError` in a test and a bare `PaymentError` at runtime may be two unrelated classes from different modules.
- Decision: `match_exception()` handles the two cases differently. A builtin expectation may use the real builtin hierarchy, which is derived by introspecting `builtins.__mro__` rather than a hand-written table, so it cannot drift from the interpreter. A qualified expectation (`pytest.raises(mypackage.MyError)`) only matches a fully qualified observation; a bare observation gives `INCONCLUSIVE`, because the test author named a specific class and the runtime cannot confirm it. A custom expectation matched only by bare name is always `INCONCLUSIVE`: two modules may define the same class name, and importing the target to find out is forbidden. When both sides are fully qualified and both are builtin, the hierarchy is applied, since `builtins` is then the only module either can be.
- Why: The builtin hierarchy is a fact about the standard library, available without touching target code, so using it is sound. Custom class identity genuinely is not determinable from an unqualified name, and guessing from filename similarity is exactly the behaviour this project refuses.
- Alternatives considered: matching any exception whose name merely ends in `Error` (matches unrelated classes); importing the target module on the host to resolve the class (host execution, forbidden since D-011); reporting a custom mismatch by name (would be a false bug report whenever two modules share a class name); a hand-written builtin hierarchy table (would drift from the interpreter and would need maintenance per Python version).
- Consequences: `test_the_builtin_hierarchy_is_derived_from_builtins_not_hand_written` pins the derivation, and `test_a_custom_exception_matched_by_bare_name_is_inconclusive` pins the refusal. Unqualified custom exceptions are therefore a permanent `INCONCLUSIVE` until a later phase adds qualified identity to the protocol.
- Files: src/edgehunter/evaluation/exceptions.py, tests/test_evaluation_verify.py

### D-062: Source snapshots are verified by SHA-256 content fingerprint; no Git commit is invented

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: Oracle evidence describes a specific revision of a file. If the source changes between the scan and the execution, a mismatch could be reported against an expectation that describes different code. The phase requires the executed revision to be provably the analyzed one, or the verdict withheld.
- Decision: `SourceSnapshot.verify()` compares the `ModuleAnalysis.digest` captured during the single read with the SHA-256 of the bytes actually staged for execution. Both must exist and be equal for `verified` to be true. Anything else yields `INCONCLUSIVE` with the reason `source snapshot not verified`. No Git commit hash is involved: a target repository may not use Git, so referencing or inventing one would be a fabrication. The staged digests are captured into `RunReport.staged_digests` before the temporary tree is deleted, so verification survives cleanup.
- Why: A content fingerprint is the only identity available for a directory that is not necessarily a repository. Comparing the analyzed bytes with the executed bytes closes the scan/execute race completely, because the staged copy is what the container actually ran.
- Alternatives considered: recording a Git commit hash (requires the target to be a repository; silently absent otherwise, and fabricating one is worse than recording nothing); re-reading the source to compare (a second read of every file, and it would race the same way); trusting the plan without verification (defeats the purpose, and the phase's rule is to withhold rather than assume).
- Consequences: The fingerprint work that Phase 6A prepared is what makes this possible. `test_source_snapshot_mismatch` and the integration test `test_the_source_snapshot_is_verified_against_the_executed_bytes` pin both directions, and `test_rechecks_reuse_the_same_source_snapshot` proves every recheck measured one revision by construction.
- Files: src/edgehunter/evaluation/repository.py, src/edgehunter/execution/models.py, src/edgehunter/execution/repository.py, src/edgehunter/execution/staging.py, tests/test_evaluation_applicability.py, tests/test_evaluation_integration.py

### D-063: Production assertions yield `ASSERTION_OBSERVED`, and guard reachability is never inferred

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: Phase 3 mined production `assert` conditions and `if ...: raise` guards as explicit evidence (D-024). Neither is a universal input contract. `assert balance >= 0` in a public function states a precondition the caller is expected to honour, and `if amount < 0: raise` existing in the source says nothing about whether that branch ran for a given input.
- Decision: A raised `AssertionError` with no applicable exact expectation produces `ASSERTION_OBSERVED`, which is reported as needing review, never as a confirmed defect. Its oracle status is `INCONCLUSIVE` because EdgeHunter cannot decide whether the caller violated a precondition. Validation guards are retained by `guard_evidence()` as explanatory context, attached to a finding's detail line, and **never evaluated**. No guard predicate is evaluated on the host: no `eval`, no import of a target helper, no invocation of a target predicate. Returning normally proves nothing about which assertions inside the function were reached.
- Why: The distinction the phase draws is between a fact about the run (an assertion fired) and a judgement about the code (the assertion was wrong). Only the first is available here. Reachability analysis is genuinely out of scope, and the optional "syntactically proven leading guard" subset the phase permits was skipped: implementing it correctly needs a formal specification of dominance and short-circuit evaluation that this phase has no budget to test exhaustively, and the phase explicitly allows skipping it when it threatens correctness.
- Alternatives considered: treating an `AssertionError` as a contract violation for any input (manufactures bug reports from preconditions, which is the single worst false-positive mode here); evaluating guard predicates over typed parameter values (forbidden: converting arbitrary AST into host code, and unsound for any non-pure predicate); inferring dominance by inspection (would need proof, and a wrong inference is a false report); inverting a guard into "the opposite condition is valid" (rejected in D-024 and still wrong).
- Consequences: `test_a_fired_assertion_asks_for_review_rather_than_claiming_a_bug` and `test_a_non_raising_return_is_never_called_a_guard_violation` pin both refusals. A target whose only oracle evidence is a production assertion will produce `ASSERTION_OBSERVED`, which is the honest maximum.
- Files: src/edgehunter/evaluation/evaluator.py, src/edgehunter/evaluation/findings.py, tests/test_evaluation_findings.py

### D-064: Conflicting applicable expectations are reported, and neither one is chosen

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: Two tests can disagree about one invocation: `assert f(1) == 2` and `assert f(1) == 3`. One of them will match whatever the runtime produced, so "pick the one that agrees" is trivially available and completely worthless.
- Decision: `reconcile()` reports `CONFLICTING_EVIDENCE` whenever applicable oracles reach different verdicts, and retains every contributing source location. A match beside a mismatch is a conflict too, because the repository's evidence is genuinely inconsistent about that invocation. The verdict maps to `FindingKind.INCONCLUSIVE`, and no defect is claimed. With a single applicable oracle the verdict passes through unchanged.
- Why: Choosing the matching oracle would make the evaluator unfalsifiable: it would always find agreement by construction. Reporting the conflict instead tells the user something actionable (their tests disagree) without claiming the code is wrong.
- Alternatives considered: preferring the matching oracle (unfalsifiable, and dishonest); preferring the first expectation in file order (arbitrary and hides the disagreement); reporting `MISMATCH` when any oracle is contradicted (a claim about the code derived from inconsistent expectations, which is the wrong conclusion); dropping the losing expectations (loses the only actionable information).
- Consequences: `test_two_conflicting_expectations_are_reported_as_a_conflict` asserts both locations survive, and the real-Docker `test_a_conflict_is_not_resolved_by_picking_the_convenient_oracle` proves it against `add(0, 0)` actually returning `0` — the observation matches one expectation and the verdict is still a conflict.
- Files: src/edgehunter/evaluation/evaluator.py, src/edgehunter/evaluation/findings.py, tests/test_evaluation_verify.py, tests/test_evaluation_integration.py

### D-065: Rechecking is opt-in, bounded, snapshot-fixed, and never counts a failure as confirmation

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: One mismatching execution is an observation. Repetition can strengthen it, but automatic retries would silently re-execute untrusted code and an environment failure could be mistaken for confirmation.
- Decision: `RunOptions.rechecks` defaults to 0 and `RunOptions.bounded_rechecks()` clamps to `HARD_MAX_RECHECKS = 5`, so total containers per plan never exceed 6. `--recheck` is the only way to request it and `--evaluate` is required alongside. Every attempt reuses the *same* staged snapshot, so all attempts measure one revision by construction. Each attempt gets its own nonce and execution id; the protocol is not weakened for repetition. `summarize_reproduction()` reports `REPRODUCED` only when every attempt reached the same verdict, `FLAKY` when attempts disagreed, `RECHECK_FAILED` when any attempt could not be evaluated, and `NOT_RECHECKED` when rechecking was not requested. A timeout, import failure, or unavailable sandbox counts as a failure and never as a mismatch. Attempts are compared by normalized observation key — outcome kind plus typed value, or exception class — never by duration, execution id, container id, or temporary path.
- Why: Every one of these rules closes a specific way of overstating. Opt-in stops surprise execution. Bounding stops runaway cost. Snapshot-fixing stops a source change between attempts masquerading as stability. Separating flakiness from reproduction stops unstable behaviour being called a stable bug. Excluding environment failures stops a broken Docker install being reported as a discovered defect.
- Alternatives considered: retrying every exception automatically (re-executing untrusted code without asking, and manufacturing stability claims); adaptive escalation of the budget (a search, not a reproduction); comparing raw JSON documents (durations and ids make every run differ, so nothing would ever reproduce); treating a failed attempt as neutral (then `MISMATCH` plus `SANDBOX_UNAVAILABLE` would read as a reproduced bug).
- Consequences: `test_three_identical_mismatches_are_reproduced`, `test_a_mismatch_match_mismatch_sequence_is_flaky`, and `test_an_unusable_attempt_fails_the_recheck_and_never_confirms` pin the three outcomes, and `test_reproduction_is_off_by_default` plus `test_recheck_counts_are_clamped` pin the bounds structurally.
- Files: src/edgehunter/execution/repository.py, src/edgehunter/execution/models.py, src/edgehunter/evaluation/repository.py, src/edgehunter/evaluation/recheck.py, src/edgehunter/evaluation/findings.py, tests/test_evaluation_findings.py, tests/test_evaluation_safety.py

### D-066: Findings carry no severity, and their identifiers are derived deterministically

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: A finding is the sentence a user reads, so it is where overstating is most tempting. Phase 3 risk scores are search-priority heuristics (D-022) and turning one into "HIGH severity bug" would be a category error.
- Decision: `FindingCandidate` has no severity field at all, and `FindingKind` has no `CRITICAL`, `CONFIRMED_VULNERABILITY`, or similar member; the safety suite asserts the vocabulary is free of them. `FindingKind` is `OBSERVED_EXPECTATION_MISMATCH`, `REPRODUCED_EXPECTATION_MISMATCH`, `ASSERTION_OBSERVED`, `SUSPICIOUS_BEHAVIOR`, `INCONCLUSIVE`. `MATCH` and `UNSUPPORTED` produce no finding at all: an unsupported comparison is a limitation the report already shows, and a finding for it would be noise. Identifiers are `ehf-` plus the first 12 hex characters of a SHA-256 over target identity, source fingerprint, oracle location, invocation, and finding category, so the same case is named identically on every run and unrelated findings cannot collide. Deduplication uses that same key and merges findings only when it matches exactly, so the same exception class on different targets, inputs, or snapshots stays distinct.
- Why: Omitting severity structurally is stronger than documenting that it is not computed: a field cannot be misused if it does not exist. Deriving the id from the identity rather than counting findings means a rerun of the same case is recognisably the same finding, and hashing rather than truncating a counter means two unrelated findings cannot share a name.
- Alternatives considered: a severity field documented as "not yet implemented" (an invitation to fill it with the risk score); a numeric confidence percentage (false precision, rejected in D-023 too); sequential identifiers per run (unstable across runs and dependent on evaluation order); dedup by exception name (merges genuinely different failures).
- Consequences: `test_every_finding_kind_avoids_severity_language`, `test_two_findings_never_share_an_identifier`, `test_deduplication_is_order_independent`, and the four "stays two findings" tests pin this. CLI tests assert the strings `CRITICAL`, `VULNERABILITY`, and `Confirmed` never appear in evaluated output.
- Files: src/edgehunter/evaluation/models.py, src/edgehunter/evaluation/findings.py, src/edgehunter/cli.py, tests/test_evaluation_findings.py, tests/test_evaluation_safety.py, tests/test_evaluation_cli.py

### D-067: `--evaluate` is additive and changes no exit code

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: Phase 6A established `run` exit codes 0/2/3 with `1` deliberately unused (D-057). Adding an evaluation flag is exactly the moment a project is tempted to add "bug found" as an exit code, which would let a caller act on a verdict without reading it.
- Decision: `--evaluate` and `--recheck` are options on `run` only. Without `--evaluate` the output is byte-for-byte the Phase 6A observation report including its "Oracle evaluation: not performed" and "Finding: none" lines. `scan` gains no evaluation flag at all. Exit codes are unchanged: `0` when something ran and was observed, `2` for invalid input, `3` for refused or unavailable. A contradiction appears only in the output, never in the status. A negative `--recheck` is invalid input (2); an oversized one is clamped to the hard maximum rather than refused.
- Why: Keeping "bug found" out of the exit status preserves D-057's property that a script can distinguish "the scan found something" from "the run did not happen", and keeps a verdict from being acted on without being read. Refusing rather than clamping a negative count is a user error worth reporting; clamping a large one is routine politeness.
- Alternatives considered: exit `4` for a confirmed contradiction (makes the tool's status carry a judgement, and "confirmed" is exactly the claim this phase refuses); making evaluation the default (silently judges code the user only asked to observe); adding `--evaluate` to `scan` (a static scan must stay static).
- Consequences: `test_without_the_flag_the_output_still_only_observes`, `test_scan_never_gains_an_evaluation_flag`, and `test_evaluate_does_not_change_the_run_exit_codes` pin the contract, and `test_evaluate_still_requires_allow_execution` confirms the flag cannot bypass authorization.

### D-068: The evaluator is a pure host-side function, and re-execution lives in the execution layer

- Date / phase / commit: 2026-10-09, Phase 6B (Runtime Oracle Evaluation), b64e97f
- Context: The phase requires that host-side evaluation execute no target code, be testable without Docker, and never bypass the existing `--allow-execution` authorization. Those three requirements are easiest to satisfy by construction rather than by discipline.
- Decision: `evaluation/evaluator.py`, `applicability.py`, `compare.py`, `exceptions.py`, `values.py`, and `findings.py` are pure functions over already-decoded observations and already-mined evidence. They start no process, import nothing from the target repository, and never evaluate a target expression: recorded literals go through the Phase 6A codec's AST whitelist, and the only values materialized are built-ins the worker already produced with exact type checks. Bounded re-execution lives in `execution/repository.py`, where authorization, staging, and the Docker backend already were, so there is no second and weaker route into a container. `tests/test_evaluation_safety.py` walks the package's own AST and fails if any module gains `eval`/`exec`/`importlib`/`subprocess`/`pickle`, imports the Docker backend or the worker, or imports `ast.parse`/`json.loads` to build its own literal grammar.
- Why: Keeping the boundary structural rather than documented means it cannot rot silently. Reusing the codec's recognizer is what guarantees a recorded expectation can never reach something that could evaluate it. Putting re-execution next to the existing runner means authorization is inherited rather than reimplemented.
- Alternatives considered: one `evaluate_and_recheck` function in the evaluation package (would have to start containers, so the whole surface would need Docker to test); a second, simpler execution path for rechecks (a weaker security boundary, which D-045 explicitly rejected); the evaluator importing target modules to resolve exception classes (host execution, forbidden since D-011).

### D-070: A recognized `bool` or `str` parameter was silently unreachable; the fix is in action applicability

- Date / phase / commit: 2026-10-09, Phase 7A (Action Coverage Repair + Exception Identity Hardening), dbb27e2
- Context: Phase 6B's handoff recorded that `bool` and `str` parameters "still produce no invocation plans" and called that "the least honest of the current behaviours", because the parameter was neither tested nor explicitly refused. The obvious suspect was the annotation parser, so the cause was verified before anything was written.
- Decision: The defect is in action applicability, not in annotation interpretation. `scanner/annotations.py` already recognizes `bool` and `str` (D-036), but `generation/actions.py::ANNOTATION_ACTIONS` listed only `list`/`tuple`/`set`/`dict`, and Phase 2's generic numeric candidates are restricted to `int`/`float` shapes (D-017, D-036). ### D-071: The action vocabulary gains `SET_FALSE`, `SET_TRUE`, and five string edge actions

- Date / phase / commit: 2026-10-09, Phase 7A (Action Coverage Repair + Exception Identity Hardening), dbb27e2
- Context: D-070 established *why* `bool` and `str` were unreachable. This records the vocabulary and the exact values, because the value table is the part a reader has to be able to audit.
- Decision: `SemanticActionKind` gains seven members: `SET_FALSE` and `SET_TRUE`; `EMPTY_STRING`, `WHITESPACE_STRING`, `UNICODE_STRING`, `NULL_CHARACTER_STRING`, and `LONG_STRING`. ### D-072: One canonical `render_string_literal()` serves every layer, and the CLI compacts for display only

- Date / phase / commit: 2026-10-09, Phase 7A (Action Coverage Repair + Exception Identity Hardening), dbb27e2
- Context: Phase 4 hand-wrote the string strategy table's spellings (`""`, `" "`, `"é"`) and `baselines.py` hard-codes `'""'`, while the new string actions need a rendering of their own. Three spellings of the same value across three layers is a latent defect, not a style issue: `generation/strategy.py::_collect_values` deduplicates by rendered text, so two spellings of one value silently produce two rows listing the same input twice.
- Decision: `render_string_literal()` in `generation/materialize.py` is the single rendering function, used by the string actions, by the strategy table, and — asserted equal to it by test — consistent with the `str` baseline. It emits a double-quoted Python literal: it escapes the backslash, the double quote, `\n`, `\r`, `\t`, and any non-printable character, and leaves printable non-ASCII literal so the recorded value reads as the documented constant. Separately, `cli.py::_display_text()` is a *presentation-only* transform applied where a value is printed: it escapes every character outside printable ASCII (so a NUL byte, an emoji, and a CJK character are never written to a terminal, independently of the host's console encoding) and compacts a value longer than 80 rendered characters to a prefix plus its true length. Neither function touches the stored `value_text`, so the codec, the plans, and the execution layer all keep the exact literal.
- Why: Verified experimentally that the `repr()` alternative really does fix the duplication: with `repr()` the strategy descriptors for `value: str` are exactly `['empty', 'space', 'unicode', 'nul', 'long']` with no duplicates. Double quotes were chosen over `repr()` because `repr("")` is `''`, which would have required editing a passing Phase 4 test *and* would have left the adversarial `''` disagreeing with the `""` baseline in the same report. Display compaction is separated from value rendering because spec section 10 requires them to stay separate: a compact preview must never truncate the value the target receives, and 1,024 characters would otherwise be printed in full by each of the actions, candidates, plans, and strategies sections. Escaping only what a terminal cannot encode also keeps `float("nan")` intact; an earlier version of this rule escaped quotes and turned `float("nan")` into `float(\"nan\")`, which broke `test_scan_lists_strategy_plans_with_flag` and was corrected.
- Alternatives considered: leaving the three layers with their own spellings (guarantees the duplicate-row defect and lets the layers drift, which is the failure D-072 exists to prevent); truncating the stored value (would corrupt the input the target receives); emitting an escaped non-ASCII form in the stored value (the stored value is the documented constant, and escaping for a terminal is the CLI's decision, not the materializer's); depending on `sys.stdout.encoding` (display would then differ between machines, which violates the determinism D-043 requires).
- Consequences: `_display_text` is applied in `_print_actions`, `_print_candidates`, `_print_plans`, and `_print_strategies`. `test_display_text_leaves_ordinary_values_untouched` pins that values already safe to print are byte-identical, so the new rule cannot silently change unrelated output.
- Files: src/edgehunter/generation/materialize.py, src/edgehunter/generation/strategy.py, src/edgehunter/cli.py, tests/test_generation_string_actions.py

### D-073: The worker reports qualified exception identity from real class metadata

- Date / phase / commit: 2026-10-09, Phase 7A (Action Coverage Repair + Exception Identity Hardening), dbb27e2
- Context: Phase 6A recorded an exception as `type(exc).__name__`, and D-061 correctly refused to match a custom class from a bare name. But a bare name also cannot distinguish the real builtin `ValueError` from a target's own `class ValueError(Exception)`, so the observation was too weak to use even for the cases Python can decide.
- Decision: The worker's result document gains four optional fields on a raised outcome: `exception_module`, `exception_qualname`, `exception_builtin` (a boolean), and `exception_builtin_lineage` (the builtin exception classes found in the class's real MRO, most derived first). They come from `_exception_identity()`, which reads only `type.__getattribute__(cls, "__module__")` / `("__qualname__")` and the class's `__mro__`, and decides builtin's identity by **class identity** against the set of exception classes in `vars(builtins)`. No `repr`, no `str`, no serialization, no import of the exception's module, and no method is called on the exception or its class. Any metadata that cannot be read safely is omitted rather than guessed, which is what keeps "unknown" distinguishable from "recorded". Module, qualname, and lineage are bounded (200 characters, 16 entries) so a target cannot make the document grow.
- Why: `type.__getattribute__` is called directly rather than `cls.__module__` on purpose: the ordinary attribute access goes through `type(cls).__getattribute__`, which for a class with a custom metaclass is *target-defined code running on the observation path*. Bypassing it means recording a class's own name never executes the class. Deciding `exception_builtin` by identity rather than by name is what makes `class ValueError(Exception)` report `False` while the real one reports `True`; the two then carry different qualified identities and can never be confused.
- Alternatives considered: `repr(exc)` or `str(exc)` for identity (both can run a target-defined override — D-048 already rejected `repr` for returns); pickling or reconstructing the class on the host (forbidden outright); importing the exception's module to resolve it (host execution, forbidden since D-011); inferring the lineage from the class name's suffix (`MyValueError` looks like a `ValueError`, and `class MyValueError(Exception)` is not one — the suffix is a guess, and the real MRO is available); changing the protocol version (see D-074).
- Consequences: `RuntimeObservation` gains four optional fields and `exception_identity_text`, which renders `myapp.errors.InvalidInput` for a custom class and `ValueError` for a builtin (the `builtins` module is omitted). The worker is rebuilt into `edgehunter-runtime:1`; an existing cached image still contains the old worker and its documents lack these fields, which the host handles as unknown (D-074).
- Files: src/edgehunter/runtime/worker.py, src/edgehunter/execution/models.py, src/edgehunter/execution/repository.py, tests/test_execution_exception_identity_integration.py, tests/test_execution_exception_protocol.py

### D-074: The result protocol stays at version 1 because the change is purely additive

- Date / phase / commit: 2026-10-09, Phase 7A (Action Coverage Repair + Exception Identity Hardening), dbb27e2
- Context: D-073 changes a result document that D-046 versioned. D-046's own rationale for versioning is "a future change detectable rather than silently misread", and D-069's is that a schema version makes a change detectable. The question is whether an additive change needs a new version, and whether old evidence must still be readable.
- Decision: `PROTOCOL_VERSION` stays `1`. The four new keys are added to `_RESULT_KEYS` and every one is optional and absent from a `returned`, `import_failure`, or `protocol_error` document. `RuntimeObservation` therefore keeps `None` for all four fields when decoding a document written before this change, and `None` means "never observed" — it is explicitly *not* read as `False`. Decoding a malformed value is refused rather than coerced: a non-boolean `exception_builtin` becomes unknown, and a lineage that is not a list of strings is dropped *entirely* rather than repaired, because a partly-trusted inheritance chain could make a non-subclass look like a subclass.
- Why: No required field changed type or meaning, so a version bump would claim an incompatibility that does not exist and, worse, a version 2 reader would *refuse* evidence a version 1 reader accepts — the exact outcome "do not reject old evidence artifacts unnecessarily" prohibits. The compatibility is tested rather than asserted: a synthetic version 1 document decodes with all four fields `None`, and it still passes the key allowlist. The new worker and the new host ship together inside one image, so a new document read by an old host cannot occur in practice. While tightening this path, `_outcome()` now clips `exception_message` itself instead of relying on the call site, so the message bound is a property of the document builder rather than of a caller remembering to clip.
- Alternatives considered: bumping to `PROTOCOL_VERSION = 2` (rejects readable evidence and asserts a break that did not happen); an unversioned second document format (explicitly forbidden); making the new fields required (would make every existing writer and every older document invalid for no gain).
- Consequences: A stale `edgehunter-runtime:1` image built before this change produces documents with no identity fields, and the evaluator therefore keeps its Phase 6B name-only verdicts for those runs. This was observed during the session: two real-Docker oracle tests failed until the cached image was removed and rebuilt, exactly as `handoff.md` warns.

### D-075: Richer observation buys lineage-based verdicts, never name-based custom matching

- Date / phase / commit: 2026-10-09, Phase 7A (Action Coverage Repair + Exception Identity Hardening), dbb27e2
- Context: The phase's stated risk is that "more exception metadata does not automatically mean more confident oracle matching". D-061 built the whole oracle on refusing to guess identity from a bare name, so adding names to the observation is exactly the change that could quietly undo it.
- Decision: `match_exception_observed()` replaces the name comparison with a decision ladder, and the string-only `match_exception()` is kept as a wrapper for observations that carry no identity. A **builtin expectation** may now conclude in three cases: against a class proven `is_builtin` (using the real hierarchy from D-061, so `UnicodeDecodeError` satisfies `ValueError`); against a class proven *not* builtin whose recorded lineage *contains* the expected builtin (so `class MyValueError(ValueError)` matches, which is what Python's own `pytest.raises` does); and against a class proven not builtin whose lineage *does not* contain it (so `class MyValueError(Exception)` is a `MISMATCH` rather than an undecided case). A **custom expectation** is always `INCONCLUSIVE`, even when the observed qualified name is textually identical, because the test module's binding of that name is unknown. A **shadowed expected name** in the test module's own source is `INCONCLUSIVE` before any of that. When the observation carries no `is_builtin` field at all, the Phase 6B name-only rules apply unchanged, so an older document is never downgraded.
- Why: The lineage is trusted exactly as far as the builtin hierarchy already is: both come from Python's own class objects, one read on the host and one read in the sandbox, and neither depends on a name. This is the difference between "the names differ" and "the inheritance chain provably does not contain it" — the first must never be a mismatch (D-061), the second is a fact and may be. The name-only fallback matters for a second reason: downgrading every un-annotated observation to `INCONCLUSIVE` would have silently narrowed what the tool can conclude about evidence it can still read, which is its own kind of dishonesty. Note the deliberate asymmetry: the lineage ladder only applies to *builtin* expectations. A custom expectation has no trusted hierarchy to walk, because its classes live in the target.
- Alternatives considered: keeping every custom expectation inconclusive and never using the lineage (loses a decidable case Python itself decides, and discards evidence the sandbox paid for); trusting the lineage for custom expectations too (there is no trusted class to compare against — the whole problem is that the expectation's class is unresolved); reporting the negative-lineage case as `INCONCLUSIVE` (a provable non-derivation is not a missing fact, and calling it unknown would discard a real contradiction); a numeric confidence score (false precision, rejected in D-023 and D-066 alike).
- Consequences: `INCONCLUSIVE` is now rarer for builtin expectations against real evidence and unchanged for custom ones. The four Phase 6B verdicts that previously depended on a bare observed name are unchanged, which the existing suite verifies. `identity_from_observation()` is the single translation from a `RuntimeObservation` to an `ExceptionIdentity`, and the `observed_description` of a raised oracle now shows the qualified identity rather than a bare name.
- Files: src/edgehunter/evaluation/exceptions.py, src/edgehunter/evaluation/evaluator.py, tests/test_evaluation_exception_identity.py

### D-076: A narrow source-level safeguard catches a test module that shadows a builtin name

- Date / phase / commit: 2026-10-09, Phase 7A (Action Coverage Repair + Exception Identity Hardening), dbb27e2
- Context: D-075 sharpens builtin identity, which raises the cost of being wrong about the *expected* side. A test module may declare `class ValueError(Exception)` and then write `pytest.raises(ValueError)`, meaning its own class; a bare spelling of a builtin name is then not evidence of anything builtin.
- Decision: `TestExpectationCandidate` gains `exception_binding: str | None`, populated by `_module_bindings()` in `oracle/test_expectations.py` from the module-scope bindings the test file already parses: a class, function, assignment, annotated assignment, `import`, or `import from` of that name. It is consulted only for a **bare** `pytest.raises(Name)`, and a recorded binding makes the expectation `INCONCLUSIVE` with a reason naming the binding. A **qualified** `pytest.raises(pkg.Name)` is never affected, because a module-level binding of the short name cannot shadow a qualified attribute.
- Why: This is the one shadowing case that is decidable from the AST EdgeHunter already has, and it is decided without importing anything. - Consequences: `test_a_dotted_expectation_checks_its_own_final_name` records the qualified/bare distinction, and the binding is threaded from mining to the evaluator with no new parsing on the host side.

### D-077: No shrinking, no adaptive search, and an exact oracle does not survive its own input change

- Date / phase / commit: 2026-10-09, Phase 7A (Action Coverage Repair + Exception Identity Hardening), dbb27e2
- Context: The deterministic candidate space grew in this phase — a `bool` or `str` parameter now has plans where it had none — which is precisely the precondition that tempts a future phase to minimise a failing input. D-059 established that an expectation applies to one exact recorded invocation, and that rule is easy to violate in a shrinker.

### D-078: An observation with no exception-identity evidence decides nothing, in either direction

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted

- Decision: When an observation reports no builtin-identity evidence (`exception_builtin is None`), a builtin expectation is `INCONCLUSIVE` — never `MATCH` and never `MISMATCH`. ### D-079: Shrinkability is a typed, one-way classification, and the refusal happens before execution

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: D-059 established that an expectation covers one exact invocation. D-077 recorded the consequence for a future shrinker but left it undecided. Phase 7B must make it executable, and the failure mode to avoid is running a smaller input and then judging it against an oracle that does not cover it.
- Decision: `ShrinkabilityKind` has five members — `REUSABLE_CONTRACT`, `EXACT_INPUT_ONLY`, `UNSUPPORTED_ORACLE`, `UNVERIFIED_SOURCE`, `INCONCLUSIVE` — and only the first permits an input change. Mined test expectations (both `assert` and `pytest.raises` shapes) are `EXACT_INPUT_ONLY`; unresolved or ambiguous callees and custom expected exceptions are `INCONCLUSIVE`; production assertions and validation guards are `UNSUPPORTED_ORACLE`. `assess_target_shrinkability()` answers the §7 question from the repository's own evidence alone, and `ShrinkRequest.contract_path` may be `None` to ask exactly that. There is no flag that bypasses the refusal.
- Why: The refusal is a *refusal*, not a deferral: no smaller input is executed and then judged against an inapplicable oracle. The test that matters proves this by spying on the attempt runner and asserting it was never called, rather than by inspecting output. A production guard is not promoted however simple its condition: `if x < 0: raise ValueError` constrains a path, not a domain, and D-063 already refuses to generalize it. `REUSABLE_CONTRACT` is deliberately unreachable from `assess_target_shrinkability()`, because a reusable oracle exists only when a contract file was explicitly selected — returning it from a function that reads only mined evidence would be a lie.
- Alternatives considered: a boolean `shrinkable` flag (a boolean cannot carry *why*, and the reason is what stops the question being re-argued); inferring a reusable contract from a simple production guard (soundness by inspection, and exactly the fabrication this project refuses); a `--force-shrink` escape hatch (the phase forbids it, and it would convert the central correctness rule into a preference).
- Consequences: `NOT_SHRINKABLE` became a reachable status — well-formed but unsound — and is distinct from `REFUSED`, which covers malformed or unauthorized input. A contract cannot be used to shrink *around* an applicable repository test: that is `NOT_SHRINKABLE` with the conflicting evidence named, preserving both sources (D-064).
- Files: src/edgehunter/shrink/shrinkability.py, src/edgehunter/shrink/models.py, src/edgehunter/shrink/repository.py, tests/test_shrink_shrinkability.py

### D-080: A user-declared contract is the only reusable oracle, and it is never discovered

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: Minimization needs an oracle that applies across a range of inputs. Every source of evidence inside a repository is exact-input or a precondition, so a reusable oracle has to come from outside the repository.
- Decision: The only source of `REUSABLE_CONTRACT` is a versioned JSON contract file the user names explicitly with `--contract-file` and `--contract-id`. It is never auto-discovered, never loaded merely because a file named `edgehunter-oracles.json` exists, and it confers no execution authorization: `--allow-execution` is still required and the contract's presence is not proof of trustworthiness. The oracle's source stays `USER_DECLARED_CONTRACT` in the result, the artifact, and the CLI output, and the CLI always prints it.
- Why: A contract is an *expectation the user asserts*, not a fact proven from the code. Blurring that distinction would let a mismatch against a user declaration be read as a discovered defect, which is the false-positive mode this project exists to avoid. Auto-discovery would make an untrusted file in a scanned repository able to steer the tool, and would mean a repository could authorize its own oracles — precisely the trust inversion the explicit flag prevents.
- Alternatives considered: inferring contracts from production guards and assertions (forbidden by the phase, and unsound: reachability is never inferred, per D-063); trusting a repository-committed contract automatically (lets the repository under test choose the standard it is judged against); supporting several contract formats (one deliberately narrow family is verifiable this phase).
- Consequences: The finding wording is fixed: a reproduced mismatch against a user-declared contract, never a confirmed defect. No severity, no confidence number, and no "confirmed bug" status exists.
- Files: src/edgehunter/shrink/contract.py, src/edgehunter/shrink/models.py, src/edgehunter/cli.py

### D-081: The contract schema is one inequality, one builtin exception, and one source fingerprint

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: The phase forbids a general property language. The schema has to be small enough that every rule in it can be checked by inspection and tested exhaustively.
- Decision: `version` is exactly `1`. One contract is: `id`, `target` (`relative/path.py::qualified_name`), `source_sha256` (64 lowercase hex), `parameter`, `domain` (`operator` in `lt|le|gt|ge` plus `integer` as a decimal string), and `expectation` (`kind: raises_builtin` plus a real builtin `exception` name). Nothing else is accepted, and any unrecognized key at any level is refused. Integers are bounded to signed 64-bit and must be written as decimal *strings*, so a JSON number cannot smuggle in a float or arbitrary precision. The expected exception is resolved against `builtins` and tested as a class, so `int`, `len`, and a same-spelling custom class are all refused.
- Why: A contract id allows hyphens because the documented example is `negative-age-rejection`; a parameter, exception, and target name must be plain ASCII identifiers because all three are looked up in code. Requiring the integer as a string is the one rule that closes both the boolean-masquerading-as-integer hole and the arbitrary-precision hole in one move. Refusing a *dotted* expected name is deliberate: D-061 never resolves custom classes, and a dotted name would imply a resolution that does not exist.
- Alternatives considered: accepting JSON integers directly (a boolean or a float slips through, and a huge integer chooses the planner's allocation); accepting a custom exception name (identity would have to be resolved, which is out of scope); allowing a contract to name several expectations (the phase requires one contract per operation, and one oracle per contract keeps the conflict rule tractable).
- Consequences: A contract file over 32 KiB, or declaring more than 64 contracts, is refused. Target paths are validated with the *existing* `check_relative_path` helper, so a contract cannot be a route around the escape rules that guard staged source.
- Files: src/edgehunter/shrink/contract.py, tests/test_shrink_contract.py

### D-082: Contract validation uses explicit character predicates, not a pattern engine

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: The first implementation validated the contract with four compiled regular expressions. The project's execution-safety suite (`tests/test_execution_safety.py`) flagged `re.compile` as a call to an execution primitive, because the rule is deliberately name-based.
- Decision: The validators are explicit character predicates — `_is_sha256`, `_is_decimal_integer`, `_is_contract_id`, `_is_identifier` — over named `frozenset` character constants, and `re` is no longer imported by the module. The safety suite was **not** weakened.
- Why: A named-predicate check over explicit character sets is readable and verifiable by eye, which matters for a module whose entire job is validating untrusted data; a pattern's escaping has to be trusted instead of read. The change also removes a dependency from a security-boundary module rather than adding an exception to a rule that exists for good reason.
- Alternatives considered: adding `re.compile` to the safety suite's allowlist (weakens a rule that has caught real things, to accommodate a stylistic choice); keeping the patterns and special-casing the module (same weakening, less honestly named).
- Consequences: `re` is absent from `shrink/`, and the acceptance behaviour is unchanged — every validation test passes with the predicates.
- Files: src/edgehunter/shrink/contract.py, tests/test_shrink_contract.py

### D-083: Domain applicability is pure integer arithmetic over four comparisons

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: A candidate must satisfy the declared domain, and the search needs to know the admissible integer closest to zero. Both must be answerable without executing or evaluating anything.
- Decision: `IntegerDomain` supports exactly `lt`, `le`, `gt`, `ge` against one integer reference, with `contains()` and `closest_to_zero()` written as four explicit cases. `closest_to_zero` is `c-1 if c <= 0 else 0` for `lt`; `c if c < 0 else 0` for `le`; `0 if c < 0 else c+1` for `gt`; `0 if c <= 0 else c` for `ge`. No AND/OR trees, no negation, no user comparator, no symbolic solver, and no unbounded search. A domain that admits no signed 64-bit integer (`x < MIN_INT`) is reported rather than approximated.
- Why: A single inequality defines a half-line, so the closest admissible value is a four-case calculation and not a search — which is what keeps the module free of any unbounded loop. `contains()` is total over every Python `int`, including out-of-range values, so an out-of-domain proposal is rejected for its value rather than because a check was missing. The eight boundary cases in the phase specification are each asserted, including the strict/non-strict distinction at every sign.
- Alternatives considered: a binary search for the anchor (an unbounded loop over an unbounded domain for an answer that is a closed-form case split); a symbolic solver such as Z3 (a dependency, and far more than one inequality needs); treating the domain as a Python expression string (evaluation, forbidden).
- Consequences: An out-of-range reference and an unsatisfiable domain are both refused before execution, so a contract cannot make the planner reason about a value the protocol could not carry.
- Files: src/edgehunter/shrink/domain.py, tests/test_shrink_contract.py

### D-084: One metric, one proposal order, and no claim of completeness

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: The search has to be deterministic, bounded, and honest about what it did not try.
- Decision: The metric is `abs(value)` and nothing else; a candidate qualifies only when its magnitude is *strictly* smaller, so equal magnitude is never an improvement in either direction. `propose_values()` returns, in order: the domain's closest-to-zero anchor (when strictly simpler), then repeated integer midpoints walking from the seed toward the anchor, deduplicated, then truncated to the budget. The midpoint walk stops as soon as a step stops making progress. There is no randomness and no unbounded binary search, and every accepted candidate is executed and verified independently.
- Why: The anchor first means the value a minimizer most wants is usually the first thing tried, so a small budget can still reach the interesting value. The midpoint walk means a very large seed closes in within a handful of containers. Nothing assumes monotonicity: a target may fail at 100, 80, and 10 and succeed at 50, so a passing midpoint says nothing about the untested values between it and the seed, and the module says so rather than inferring.
- Alternatives considered: proposing midpoints only (a large seed would never reach small magnitudes within a small budget); a random or value-based ordering (non-deterministic product output, forbidden since D-043); searching for a true global minimum (an unbounded loop, and the phase explicitly forbids claiming it).
- Consequences: The result is described as the smallest input *this bounded search verified*. `NO_SMALLER_CASE_FOUND` means the proposal list ran out, and `BUDGET_EXHAUSTED` means a budget stopped the search; `proposals_exhausted` is recorded separately from `status` so a budget stop can never be read as a completed search.
- Files: src/edgehunter/shrink/proposals.py, src/edgehunter/shrink/models.py, tests/test_shrink_contract.py

### D-085: A reduced input must preserve the observed failure character, not merely contradict the contract

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: A contract expects a builtin exception. If the original call *returned* where one was expected, then a trial that raises `TypeError` also contradicts the contract — but it is a different observed behaviour, and reporting it as a reduction of the original would be misleading.
- Decision: `FailureSignature` records the outcome category, the observed exception's qualified identity, and the sandbox's builtin flag. A normal return matches only another normal return; a raised exception must have the same observed identity *and* the same builtin status. An infrastructure outcome has **no** signature and therefore cannot be compared at all. Exception messages, durations, execution ids, container ids, and temporary paths are never part of it. The seed's signature is the reference every candidate is compared against.
- Why: Requiring the same observed character is what stops the minimizer from swapping one failure for an unrelated one just to obtain a smaller input. Excluding messages and timings is the point: none of them is a property of the failure. An infrastructure failure having no signature is what makes "a timeout" unusable as a comparison basis rather than merely unlikely to match. The identity comparison is an observation comparison, not a proof that two classes are identical, and it inherits the limitation D-061 records for custom classes.
- Alternatives considered: comparing only "did it contradict the contract" (this is the naive version, and it is exactly the swap the rule exists to prevent); comparing the full observation identity including the message (a message embeds a value, a path, or an address, so it would make two identical failures look different); accepting a raise anywhere a raise was expected (loses the distinction between "returned instead of raising" and "raised something else").
- Consequences: A candidate whose failure character changes is rejected with `SIGNATURE_MISMATCH` and the search continues, which is verified against a real container in integration test D.
- Files: src/edgehunter/shrink/signature.py, src/edgehunter/shrink/repository.py, tests/test_shrink_search.py, tests/test_shrink_integration.py

### D-086: The seed must contradict the contract reproducibly before any proposal is executed

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: A single mismatch is one observation. Minimizing an input that turns out to be flaky would produce a reduction of something that is not a counterexample.
- Decision: The seed is executed `reproduction_attempts` times (default 2, hard maximum 3) and every attempt must be a `MISMATCH` with one agreed signature. The three refusals are kept distinct: the contract being *satisfied* is `ORIGINAL_NOT_FAILING`; attempts that disagree — including one mismatch and one match — are `ORIGINAL_NOT_REPRODUCIBLE`; an attempt that could not be judged is `INCONCLUSIVE`. No proposal is generated until all of that holds, and a budget too small to cover the seed attempts stops the operation before the first container.
- Why: Distinguishing "the contract was satisfied" from "the attempts disagreed" matters because they are different facts: the first means there was never a counterexample, the second means there may be one but it is not stable. Collapsing them would let a reader believe a flaky input was a real one. Requiring the reproduction *before* proposing anything is what stops a flaky seed from generating a whole search.
- Alternatives considered: reproducing only the accepted candidate (a flaky seed would then anchor the entire search); treating a single match as a pass (the whole point is the opposite); retrying on timeout (an unbounded loop, and a timeout is not evidence either way).
- Consequences: The default cost of a shrink operation is two containers before any proposal. Every attempt, including unusable ones, counts against the execution budget; none of them is ever counted as a mismatch.
- Files: src/edgehunter/shrink/repository.py, src/edgehunter/shrink/models.py, tests/test_shrink_search.py, tests/test_shrink_integration.py

### D-087: One execution route, one staged snapshot, reused rather than rebuilt

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: The shrinker needs many containers for *different inputs* against *one* source revision. The existing `run` command already stages once and re-executes against that one copy for its rechecks, but it selects plans rather than accepting arbitrary values.
- Decision: `execution/repository.py::_execute_one` was split so the container-running half is a single function, `_run_request`, which both the plan route and the new `SessionAttemptRunner` call. `ExecutionSession` and `open_session()` expose a staged snapshot that a whole operation reuses, and `open_session` performs the same authorization, availability, and image checks `execute_target` performs, in the same order. The seed's value travels as a typed protocol integer, not rendered text, and the target reference, request encoding, nonce, Docker hardening, timeout, bounded capture, result decoding, and container cleanup are all the existing code.
- Why: A second execution route would be a second, weaker boundary, which D-045 rejected outright. Extracting `_run_request` rather than copying it means there is exactly one place that starts a container for either command, so a hardening change cannot reach one and miss the other. Staging once is what makes every attempt provably measure the same source revision, which is the same property D-062's snapshot verification depends on; the shrinker reuses `SourceSnapshot.verify` rather than reimplementing the comparison.
- Alternatives considered: calling `execute_target` once per proposal (a new stage and a new snapshot per attempt, so observations from two revisions would be compared against each other); writing a shrink-specific runner (a second boundary, and the phase forbids it); re-reading the source per attempt (a race, and a second read the single-parse design avoids).
- Consequences: The public Docker surface grew by one class and one function, and no existing behavior changed — the 43 existing execution tests pass untouched. All 61 shrinker unit tests and all 10 real-Docker shrink tests pass through this single route. Only `runtime/worker.py` still imports target code.
- Files: src/edgehunter/execution/repository.py, src/edgehunter/shrink/repository.py, tests/test_execution_integration.py

### D-088: A generator is detected from its unrepresentable return, not from a second parse

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: The phase supports only top-level synchronous functions and excludes generators. `FunctionInfo` has no generator flag, and adding one would mean re-parsing source in the shrinker, which breaks the single-parse design D-021 established.
- Decision: A generator is excluded by observing the result. A call to a generator returns an object the protocol cannot represent, so the worker reports `opaque_return`; `evaluate_against_contract` treats that as `UNSUPPORTED` with a reason naming it, and the candidate is rejected as `ORACLE_NOT_APPLICABLE`.
- Why: This is an *observed* fact rather than a static guess, and it needs no new parsing. It also covers the general case for free: any return the protocol cannot describe is not a normal return, so it must not be read as "the target returned instead of raising" — which would have manufactured a mismatch.
- Alternatives considered: adding an `is_generator` flag to `FunctionInfo` (a scanner change and a second traversal for a property the observation already reveals); re-parsing the module in the shrinker (reintroduces a second parse and a race); detecting it by call return type alone on the host (the host never sees the return value).
- Consequences: A generator target is refused with a clear reason instead of producing a false mismatch. `test_an_unrepresentable_return_is_not_a_normal_return` covers it.
- Files: src/edgehunter/shrink/repository.py, tests/test_shrink_search.py

### D-089: Statuses, exit codes, and wording that cannot be read as a verdict

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: D-057 reserved exit code `1` for `run` and D-066 removed severity from findings. A new command that reports a counterexample needs the same discipline.
- Decision: `ShrinkStatus` has eight distinct members: `SHRUNK`, `NO_SMALLER_CASE_FOUND`, `BUDGET_EXHAUSTED`, `NOT_SHRINKABLE`, `ORIGINAL_NOT_FAILING`, `ORIGINAL_NOT_REPRODUCIBLE`, `INCONCLUSIVE`, `REFUSED`. `BUDGET_EXHAUSTED` is never reported as `SHRUNK`, and `proposals_exhausted` is recorded separately from the status. The `shrink` command exits `0` when the operation completed (whatever the result), `2` for a refusal of user input, and `3` when execution was unavailable — never `1`, which stays reserved for "scan found issues". The CLI always prints the oracle source and ends with an explicit statement that the result is a reproduced mismatch against a user declaration, not a proof of a defect and not a claim of global minimality.
- Why: The exit code is not a verdict. Putting the outcome only in the structured result means a script cannot act on "a bug was found" without reading the output, which is the property D-057 established for `run`. Keeping `1` reserved means a caller can still distinguish "the scan found something" from "the shrink did not run". Wording is part of the correctness contract here: "reduced counterexample against a user-declared contract" and "smallest verified input found during this bounded search" are accurate, while "globally minimal" and "confirmed bug" are not.
- Alternatives considered: exiting non-zero on `SHRUNK` so a script could branch on it (that makes the exit code the verdict, which is exactly what D-057 rejected); merging `BUDGET_EXHAUSTED` into `SHRUNK` (would report a cut-short search as a completed one); a confidence percentage alongside the status (false precision, rejected in D-023 and D-066).
- Consequences: The CLI's own output is asserted in `tests/test_shrink_cli.py` for each refusal, and `test_the_shrink_command_never_exits_one` pins the reserved code.
- Files: src/edgehunter/shrink/models.py, src/edgehunter/cli.py, tests/test_shrink_cli.py

### D-090: The shrink artifact is versioned, evidence-only, and shares the run-id sanitizer

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: A minimization result needs to be reviewable later, and the Phase 6B artifact infrastructure already established what belongs in such a file and where it lives.
- Decision: `shrink_artifact_document()` produces strict JSON with its own `schema_version` (distinct from the execution protocol version and from the contract file version), written to `.edgehunter/runs/<run-id>/shrink.json` on request. It records target identity, source-snapshot verification, the contract id, the contract file's SHA-256, the explicit user-declared provenance, the seed and its origin, the reduced value, the status and reason, the policy and budget with the metric named, and every attempt with its outcome and rejection reason. It excludes captured stdout, captured stderr, and exception messages, and the run id is sanitized by the *same* function the Phase 6B artifact uses.
- Why: Reusing `_safe_run_id` means a crafted id is sanitized identically wherever it is used, rather than by a second rule that could be weaker. Excluding target output keeps the artifact from becoming the place secrets accumulate, which is D-069's reason and applies unchanged. Recording every rejected attempt, with its reason, is what makes "this is a bounded search" verifiable rather than a claim.
- Alternatives considered: including captured output for convenience (accumulates sensitive data for no diagnostic gain); a database (a run-management system for one small file); writing outside the ignored directory (risks committing generated artifacts).
- Consequences: `.edgehunter/` is already Git-ignored, verified with `git check-ignore`. A test asserts the artifact contains no `captured_stdout`, `captured_stderr`, or `exception_message` and no Python-object markers.
- Files: src/edgehunter/shrink/repository.py, src/edgehunter/evaluation/repository.py, tests/test_shrink_search.py

### D-091: The shrink package adds no dependency and reaches no new execution primitive

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: The phase's dependency policy expects no new dependency, and the project has a structural safety suite that fails if a new module gains an execution primitive.
- Decision: No dependency was added. The contract parser uses the standard library's `json` with a duplicate-key hook; the domain, proposals, signature, and shrinkability modules are arithmetic and comparisons; the orchestrator imports `execution` and `evaluation` and adds no `subprocess`, `importlib`, `pickle`, `eval`, or `exec`. `shrink/repository.py` deliberately does **not** import `subprocess` even to report container cleanup, because a test asserts the shrink package never starts a process.
- Why: Everything needed was already available. The safety suite caught a real collision during development — `re.compile` and a protocol method named `run` — and the resolution was to change the *implementation* (explicit predicates, and `execute_attempts`) rather than to widen the rule. That is the intended direction: the rule is a constraint on the design, not an obstacle to it.
- Alternatives considered: Hypothesis (forbidden, and nothing samples); Z3 or SymPy for the domain (a dependency for a four-case calculation); a Docker SDK (forbidden, and the existing CLI-based backend is the boundary D-045 established).
- Consequences: `pyproject.toml` is unchanged and `typer` remains the only runtime dependency. A test walks the shrink module's AST and asserts no execution primitive, no deserializer, and no dynamic import.
- Files: src/edgehunter/shrink/, tests/test_shrink_search.py, pyproject.toml (unchanged)

### D-092: The shrink command is an explicit, opt-in, bounded operation, never implicit in `run` or `scan`

- Date / phase / commit: 2026-10-09, Phase 7B (Shrinkability Contracts + Counterexample Minimization), uncommitted
- Context: A command that produces reduced inputs is where overstatement is most dangerous, so its authorization, limitations, and exit codes must be visible rather than hidden in the execution output.
- Decision: `edgehunter shrink` requires `--target`, `--contract-file`, `--contract-id`, and `--start-int`, plus `--allow-execution`. There is no `--force-shrink`. Exit `0` means the bounded search completed with whatever result it produced; exit `2` means invalid input (missing file, unknown contract id, fingerprint mismatch, out-of-domain seed, unsupported target shape, missing authorization); exit `3` means `SANDBOX_UNAVAILABLE`. Exit `1` remains reserved for `scan` and is never used by `shrink`, so a script cannot confuse a scan issue with a shrink refusal. The CLI output always names the contract id, the user-declared provenance, the metric (`abs(value)`), the budget, the proposal count, the executions consumed, the reduced value, the failure signature, and an explicit statement that the result is a bounded-search counterexample, not a proven minimum or a confirmed defect.
- Why: The contract file is selected on the command line (`--contract-file`), not discovered. Without the file nothing is executed, and the file is validated before any container starts, which is what makes the refusal structural rather than procedural. Naming `user_declared_contract` on every output line is what keeps the user declaration from being read as repository evidence.
- Alternatives considered: making the shrink implicit in `run` when `--evaluate` finds a mismatch (would make minimization automatic, which violates the phase's refusal rules and creates an unbounded loop); deriving contracts from production code (unsound and against D-079/D-084); deriving contracts from existing tests (exact tests are not shrinkable, so it would refuse everything); using a generic `--shrink` flag without `--contract-file` (no reusable contract, so nothing could shrink truthfully).
- Consequences: `tests/test_shrink_cli.py` asserts the authorization refusal, the invalid-contract refusal, the reserved exit code, and the provenance wording; the artifact writer uses the same `_safe_run_id` as the evaluator.
- Files: src/edgehunter/cli.py, tests/test_shrink_cli.py
